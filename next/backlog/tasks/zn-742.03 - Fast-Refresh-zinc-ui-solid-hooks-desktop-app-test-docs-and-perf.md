## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Done 2026-10-16 (worktree agent). What and where: docs/reports/zinc-next-fast-refresh.md §11.

- Proxies: hot-mode JSX wraps Solid calls to project components as _hotC('@hot:Tag', () => Tag(...)) (also inside _comp); the loader resolves the marker to the declaring module's path (through re-exports). _hotC (lib/std/solid.ts) renders under a root owned by the caller's owner; its if (import.meta.hot) block listens to beforeUpdate (dispose root, release the fragment's nodes) and afterUpdate (render again, same owner); listeners leave through import.meta.hot.off (new in zinc:hot) from a cleanup on the owner. Hooks iterate copies.
- render() in hot mode renders under an owner; a second render() disposes the first tree and its root node (one global, hotTree, in other builds).
- Boundary rule (owner report, coordinator 2026-10-16): a module exporting only functions, classes, interfaces, type aliases is a boundary; only exported values (let, var, non-function const) re-run importers. game-2d scenes.ts edits keep the round.
- QuickJS child writes 'hot off <why>'; zinc dev prints 'restart: the program runs on QuickJS, which has no Fast Refresh'. AOT: zinc dev always interprets (help, docs/dev-mode.md).
- frontend::libraryModule (modules.h) replaces hot.cpp's libraryPath.

Decision text (for the coordinator, D-number to allocate): Fast Refresh components and boundaries (ZN-742.03). Project components (declared in the file or imported by a relative path) get a _hotC proxy in hot mode only; it disposes and re-renders its instance under the same owner when the declaring file runs again, so parents and siblings keep their state (solid-refresh). A module exporting only code and types is a boundary: importers are bound by symbol and live objects move to the new classes by key (D123), so only exported values re-run importers. Deviation from React Native, which re-runs the importers of any module exporting more than components. The desktop-app's state.ts, router.ts and main.tsx still restart on their top-level effects: re-running state.ts resets the state a refresh keeps, a name allow-list cannot tell replacing calls from stacking ones, an empty dispose in the template would teach silencing the check; main.tsx restarting matches RN's index.js. Revisit if users edit state modules often (then undo effects with import.meta.hot.dispose in the template).

Deviation: the in-process red box is not built (a compile error still replaces the program by the red-box program, state lost): the frame-end hook cannot draw over a frame zinc:ui kept; needs a draw path for the paused program. later.md line below.

Proof: tests/run --only fast_refresh PASS (~15 s; fails on the binary before: 'a callback of src/pages/notes.tsx from before the change is still alive'); hot_swap PASS (new check: the first tree's effects stop when the entry runs again; fails before); asset_reload PASS (new check: scenes.ts colour edit keeps play scene, score and round clock, same pid; fails with the old boundary rule: 'the round started again'); hot_off, dev_mode, jsx, solid_props, nuxt_ui, modules, affected_paths PASS. Hot and non-hot desktop-app frame 10 identical.
Measured (this Mac, other trees building): save to first new frame 523-565 ms for a desktop-app page (42 files; restart ~570 ms loses state), 96 ms game template, 60-300 ms hot_swap fixtures. Perf log line for docs/reports/zinc-next-perf.md: 'ZN-742.03 Fast Refresh: desktop-app page save -> first new frame 523-565 ms (state kept), game template 96 ms'.
