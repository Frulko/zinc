## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
After ZN-590.02, LINE/POLY fills go through the stencil on the GPU except the canvas gradient paint record (grad 4: linear or radial, n stops), which keeps the CPU coverage tiles: examples/canvas/sketch still rasterizes 16.7 tiles a frame on the CPU (3.9 ms to submit). Draw it on the GPU (the stops in a small texture per command, t from the paint geometry in the shader), and batch consecutive POLY commands whose boxes do not overlap into one set of passes (lottie-gallery issues 598 draw calls a frame, 7 per POLY).
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Done: runtime/gl_replay.cpp. (1) The canvas gradient paint (grad 4) is computed by the main shader for a POLY's cover and fringe passes (raster.cpp paint_at: linear or two-circle radial t, the stop interval, lerp_color's weight out of 256, the stop alpha), stops in uniforms (u_g0/u_g1 geometry, u_gc colours, u_go offsets), up to 8 stops; more stops or no stencil keep the CPU tiles. (2) fill_gpu became poly_add/poly_flush: consecutive POLYs whose boxes (+1 px) are apart, with the same fill rule and no gradient, share one set of passes (up to 64 shapes per batch, 7 draw calls); each keeps its depth.
Measured (display-gl, ZINC_DETERMINISTIC, 300 frames, before -> after, back to back): canvas/sketch 28.1 -> 0 CPU tiles per frame, submit 8.87 -> 1.18 ms, draw calls 97 -> 208 (a gradient POLY is a batch of its own); lottie-gallery 610.5 -> 448.5 draw calls, submit 2.52 -> 2.25 ms; svg-gallery 228.8 -> 172.5, 0.96 -> 0.88 ms. glcompare GL vs software: sketch 0.85%/0.60 -> 0.87%/0.63, lottie and svg identical. Logged in docs/reports/zinc-next-perf.md.
Tests: tests/t1/gl_renderer.sh now also checks canvas/sketch at frame 300 (0.0 tiles, 5%/3 limits): PASS; gpu_strokes PASS; three_gpu PASS.
Not done (no follow-up needed now): gradient POLYs are not batched together (their paint is per-command uniforms); lottie's shapes overlap, so most of its POLYs stay one per batch.
