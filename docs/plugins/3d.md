# zinc:3d — 3D on the CPU, and on the GPU where there is one

`plugins/3d` renders simple 3D scenes on the CPU, on every target that runs the 2D rasterizer, and on the GPU on macOS (see
[GPU renderer](#gpu-renderer)). The scene graph, camera and math are Zinc code (`plugins/3d/index.ts`); transform, lighting, clipping and
rasterization are C++ (`plugins/3d/native/render3d.host.cpp`). `plugins/three` draws through zinc:3d, so it gets both. A frame is rendered into a **runtime image** (`raster::dyn_wrap`) that
`render()` adds to the frame as an ordinary image command (like `gfx.drawImage`, nearest-neighbour when scaled), so 2D
drawing and `zinc:ui` compose over it.

```ts
import { onFrame, width, height, image, drawText, font } from 'zinc:gfx';
import { Scene, Camera, Node, Material, Light, cube, render } from 'zinc:3d';

const scene = new Scene();
scene.lights.push(new Light(-0.5, -1, -0.6, 0xffffff));
const crate = new Material(0xffffff);
crate.texture = image('crate.png');                 // baked asset, or gfx.createImage() for a runtime texture
const box = scene.add(new Node(cube(1), crate));
const camera = new Camera().setPosition(0, 1.5, 4).lookAt(0, 0, 0);
let t = 0;

onFrame((dt: number) => {
  t += dt;
  box.setRotation(0, t, 0);
  const tris = render(scene, camera, 0, 0, width(), height());   // 3D view
  drawText(font('sans', 12), 8, 8, `${tris} triangles`, 0xffffff, 255, 0);  // 2D over it
});
```

Examples: `examples/3d/cubes` (textured cubes with a baked PNG and a runtime image painted with `zinc:gfx`, a Gouraud
torus, a flat-shaded sphere, a textured floor, fps overlay) and `examples/3d/model` (an OBJ model with vertex colours
and computed normals on a checkered floor; A toggles orthographic, B flat shading).

## API

| | |
| --- | --- |
| math (flat `number[]`, column-major) | `mat4()`, `mat4Multiply(out, a, b)`, `mat4Compose(out, pos, quat, scale)`, `mat4LookAt(out, eye, target, up)`, `vec3Dot/Cross/Normalize`, `quatFromEuler(x, y, z, out)`, `quatFromAxisAngle(ax, ay, az, angle)`, `quatMultiply(a, b)`, `rgb(r, g, b)` |
| `Mesh` | `new Mesh(positions, indices, normals, uvs, colors)` (empty `normals`: smooth normals computed; `uvs`/`colors` may be empty), `vertices`, `triangles`, `dispose()`. Counter-clockwise front faces, uv origin at the image's top-left, textures repeat |
| primitives | `cube(size)`, `sphere(radius, segments, rings)`, `plane(width, depth, sx, sz)` (texture repeats per cell), `torus(major, minor, segments, sides)` |
| OBJ | `parseObj(text)`, `loadObj(asset)` (from `zinc:assets`): `v` (+ optional `r g b`), `vt`, `vn`, `f` with any polygon size and negative indices; `mtl`, groups and smoothing groups are ignored. | .zmesh | `loadModel(asset)` (ZN-441): a model the asset build made for zinc:3d (a `model` rule with `"format": "zmesh"`, `docs/reports/zinc-next-assets.md` "Models": `assets/ship.glb` becomes the entry `ship.zmesh`) becomes a `Node` whose children are its parts. Each part is a mesh in the renderer's own layout (float positions and normals, uvs, 0xRRGGBB colours, 16-bit indices: `include/zn/zmesh.h`), handed to the renderer as it is (`Mesh(..., zmesh, at)`: a copy, no parsing; the GPU renderer uploads the arrays as they are), with its material (base colour and opacity, texture, double sided, unlit, blending, flat shading without normals) and its texture (an image entry beside the model, through the texture importer). The scene is flattened at build time (no node hierarchy, animations or skins); LODs are entries of their own (`ship.lod1.zmesh`) |
| glTF | `loadGltf(asset)` from `zinc:3d/gltf` (ZN-658): a `.gltf` (with its `.bin` and image files) or `.glb` from the assets or the file system becomes a `Node` whose children are the default scene's roots, with their hierarchy (TRS or matrix). Meshes: triangles, strips and fans with positions, normals (none: flat shading), uvs and vertex colours, split in meshes of 65535 vertices when larger (scans); materials: base colour, its texture (embedded images decoded at run time, image files in the assets baked), double sided, `KHR_materials_unlit`. Skins, animations and other extensions are named in a warning; a file that requires an extension the reader does not know is an error; what gltfpack writes reads too (`KHR_mesh_quantization`, `EXT_meshopt_compression`, `KHR_texture_transform`, ZN-441). It reads through the three plugin's glTF reader (decisions D25, D72) and is a module of its own: a program that does not import it links no glTF code (+194 KB when it does) |
| `Material` | `new Material(color)`; `color`, `texture` (image id, -1 none), `vertexColors`, `shading` (`Shading.Smooth` Gouraud, `Shading.Flat`, `Shading.Unlit`), `doubleSided`, `specular` (highlight colour, 0 none) and `shininess` (Blinn-Phong exponent, 30), `filter` (`Filter.Default` the renderer's `filter` option, `Filter.Nearest`, `Filter.Linear`, `Filter.Mipmap`: how the GPU samples the texture; the software renderer always takes the nearest texel), `emissive` (light the material gives by itself, 0xRRGGBB, 0 none: added to the light it receives, before its texture), `blend` (`Blend.Opaque`, `Blend.Alpha` over what is behind with `opacity` 0..1, `Blend.Add` added to it: glows, light pools, sparks; blended nodes are drawn after the opaque ones in scene order, depth tested, without hiding what comes after) |
| `Light` | `new Light(dx, dy, dz, color)`: directional, the direction light travels; up to 4 per scene, plus `scene.ambient` |
| `Node` | `new Node(mesh, material)` (both may be null: a group), `position`, `rotation` (quaternion), `scale`, `setPosition/setRotation(euler)/setScale`, `add(child)`, `visible`, `world` (updated by `render`) |
| `Scene` | a root `Node` with `background`, `ambient`, `lights` |
| `World` | `new World(asset, defaults?)`: a static world (a city, a terrain) from a `.zworld` index and its `.zwc` chunks (`include/zn/zworld.h`; the asset rule `"as": "world"` makes one from glTF, see "Large static worlds"), with the machine's `defaults3D()`, added to a scene as a node. Cells on the ground with up to three levels (near, mid, far), each level in chunks loaded and freed as a whole; a chunk's batches keep their indices grouped by cell and by the compass sector a wall faces. `select(camera, aspect, ahead, dt)` chooses natively what the next render draws: the cells in the frustum, each at the level of its distance (`nearReach`, `midReach`, coarser only past the distance times `hysteresis`), a cell whose level is not loaded showing a coarser one or else a finer one (no holes), of its walls only the sectors that can face the eye (`sectors`), and the reaches brought in when the frame passes `budget` triangles (Pocket Tokyo's governor). It leaves `triangles`, `draws`, `reachScale`, `missing` (chunks to `load(k)`, coarsest level and nearest first, for the eye and the points `ahead`) and `unused` (chunks nobody wanted for `idle` seconds, to `free(k)`); `serve(ms?)` does both within `readMs`. The draw is a list of index ranges in batch order, the state set only between batches; `setNight(night)` (0 to 1) swaps each batch's night picture and glow at 0.5, or mixes them by it (the 3DS's combiners, the PSP's clut8 palettes); `shadows(heights, ...)` darkens the ground and roofs the scene's first light does not reach (the 3DS, the PSP) and `clearShadows()` turns them off |
| `Camera` | `position`, `target`, `up`, `fov` (degrees), `near`, `far`, `ortho` + `height` (world units), `pixelRatio` (pixels rendered per logical pixel; 0, the default, is the window's pixel scale on the GPU, sharp on a Retina screen, and 1 in software), `setPosition`, `lookAt`, `dispose()` (frees its render target) |
| `render(scene, camera, x, y, w, h)` | renders into the camera's target and draws it in the screen box; returns the triangles rasterized |
| `gpu()` | whether a GPU draws the scenes (desktop GL, a console's GPU renderer) or the software rasterizer |

Each camera owns its render target, so split screens use one camera per view. Shading: lighting is computed per vertex
(Gouraud) or per face (flat) as `base × (ambient + Σ max(0, −n·L) × light)`; textures are modulated by it. The scene
graph works in any number profile: under fx12 (PS1 profile) the world matrices are composed in Q20.12 in Zinc, then the
C++ side works in float.

## Rasterizer

- vertices transformed and lit once per draw (float), outcodes against 6 planes; triangles fully outside one plane are
  dropped, the others are clipped (Sutherland–Hodgman) against the near and far planes and a guard band of ±2 viewports;
- backface culling in screen space (`doubleSided` disables it);
- blending and emissive (ZN-696): a blended triangle is depth tested and writes no depth; over: `(c × a + d × (255 − a)) / 255`, added:
  `d + c × a / 255`, clamped, on both renderers (the GPU's frame equals the software one on tests/data/zinc3d_glow). Opaque draws keep
  their code: on the GPU the emissive and blended draws use shader variants of their own;
- highlights (ZN-563.04): Blinn-Phong with three.js's `BRDF_BlinnPhong` factor, `specular × lightColour × n·l × (shininess/2 + 1)/4 ×
  (n·h)^shininess` added to the lit colour per vertex (per pixel on the GPU); a cube's flat faces barely show them in software;
- scanline rasterization, top-left rule at pixel centres, edges and attributes stepped in 16.16 fixed point;
- depth: NDC z in Q30, stored in a 16- or 32-bit z-buffer;
- texturing is perspective-correct every `subdiv` pixels (exact u/w, v/w, 1/w at the run ends, affine inside a run):
  16 is visually exact at these resolutions, larger values trade accuracy for fewer divisions;
- optional 2x2 ordered dither to RGB565 (for 16-bit panels).

Four inner loops are instantiated (textured or not × Gouraud or constant colour).

## GPU renderer

`plugins/3d/native/render3d.gl.cpp` (ZN-563) implements the same native interface on OpenGL 3.2 core (macOS) and is written against the
GLES 3 subset; it includes the software renderer, which stays the fallback and the oracle. It reproduces the software shading:

- one vertex array per mesh (position, normal, uv, colour interleaved; the software renderer builds the mesh, normals included, then its
  arrays are freed), one program per kind of material: unlit (three's `MeshBasicMaterial`) or lit (Lambert: ambient + 4 directional lights
  per vertex, clamped, like the software renderer), smooth or flat (the face normal from the derivatives of the world position), textured or
  not (nearest texel, repeat), vertex colours or not, highlights or not (per pixel, from the world normal and the eye position); the uniforms are the model and model-view-projection matrices, the colour and the
  lights (once per program and frame);
- depth test, back faces culled unless double-sided, colour interpolated in screen space (`noperspective`) like the software spans;
- the target is a framebuffer read back into the same runtime image, presented the same way. The read is asynchronous (a pixel buffer per
  target, mapped one frame later: the image shows the previous frame, as `gl.zincPresent` does); deterministic runs read synchronously
  (`ZINC_GL_PRESENT=sync|async` chooses, as for WebGL). The shaders write blue first so that the RGBA bytes read back are the runtime's
  `0x00RRGGBB` words: a `GL_BGRA` read made the driver convert on the CPU, synchronously (2.5 ms at 800x500 on the Intel Mac);
- `render()` returns the triangles submitted (three.js's `renderer.info` counts so), the software renderer those drawn after culling.

Not done yet: the GLES 2 path (no vertex arrays) and contexts on Linux, the Pi and the web (follow-up tasks).

**PS Vita (GXM).** `plugins/3d/native/render3d.vita.cpp` draws on the context of the 2D replay (`targets/vita/gxm_vita.cpp`). Positions, uvs
and indices go to GPU memory at `meshCreate`; the shading is the software renderer's own code (`Engine::shade`), per vertex on the CPU into a
colour stream of the draw (lit, flat, unlit, vertex colours, highlights per vertex, emissive, Alpha and Add blending), because the open shader
compiler the Vita has (psp2spvc, `targets/vita/shaders/README.md`) compiles no branch nor texture sampling. The GPU transforms, tests depth,
culls, textures (SDL's texture fragment program) and blends. A target is a colour surface with its own depth buffer, drawn in its own scene;
`present()` emits its IMAGE command and the 2D replay samples the surface itself, in the 2D order, with no read back. Textures filter nearest
or linear (no mipmaps); a 2D frame the replay leaves to software shows the target black.

## Options and memory

`zinc.json`: `"plugins": { "3d": { ... } }`, or per target under `targets.<id>.plugins.3d`.

| option | default | meaning |
| --- | --- | --- |
| `scale` | 0 | internal resolution divisor (software renderer; 0 = auto: the smallest divisor, 1 to 8, that keeps the picture under 400,000 pixels, so 1920x1080 is drawn at 640x360; a deterministic run keeps 1): a `w`×`h` box renders at `w/scale`×`h/scale` and is scaled up with nearest-neighbour sampling (the cheap 16.16 path of the 2D rasterizer) |
| `zbits` | 0 | 16 or 32; 0 = 16 on ESP32, 32 elsewhere. 16 bits with near 0.1 / far 100 resolves ~1.5 cm at 10 units |
| `dither` | false | 2x2 ordered dither to RGB565 |
| `subdiv` | 16 | perspective correction step in pixels |
| `renderer` | `auto` | `software`, `gpu`, or `auto`: the GPU where the target has the backend (macOS) unless the run is deterministic (`ZINC_DETERMINISTIC`: the goldens are the software frames). `ZINC_3D=software\|gpu` overrides it; without a GPU context the software renderer draws |
| `msaa` | `4` | GPU only: samples per pixel of the multisampled frame (0 or 1: none; at most what the context offers). `ZINC_3D_MSAA` overrides it |
| `filter` | `mipmap` | GPU only: how textures are sampled when a material does not say: `nearest`, `linear`, or `mipmap` (trilinear, mipmaps built at the first use). `ZINC_3D_FILTER` overrides it; three's `Texture.minFilter` / `magFilter` choose per texture (three.js's defaults: mipmaps) |

Memory per camera, allocated on the first `render` and on resize, freed by `camera.dispose()`:
colour `4 × W × H` (the runtime image) + depth `2 or 4 × W × H`, with `W = w / scale`, `H = h / scale`.

| view | colour | z16 | z32 |
| --- | --- | --- | --- |
| 160x120 (320x240, scale 2) | 75 KiB | 37.5 KiB | 75 KiB |
| 320x240 | 300 KiB | 150 KiB | 300 KiB |
| 640x360 (1280x720, scale 2) | 900 KiB | 450 KiB | 900 KiB |

Also: meshes `24 B/vertex` (+8 uv, +4 colour) + `2 B/index` (at most 65535 vertices per mesh), a per-vertex scratch of
`37 B × the largest mesh`, and a 0x00RRGGBB copy of each baked image used as a texture (`4 × w × h`, made on first
use; runtime images are sampled in place). Buffers come from system memory (`hal_alloc`) first and fall back to the
Zinc heap, which on ESP32 owns the largest free block; when both are full the program panics with
`out of memory (heap budget …)`.

ESP32 without PSRAM: the Zinc heap gets about 94 KiB (the largest free block after ESP-IDF, the display bands and
FreeRTOS) and system memory is fragmented into blocks of ~13 KiB, so a 320x240 screen takes `scale: 3` (a 106x80
view: 33 KiB colour + 17 KiB z16). `scale: 2` (160x120, 112 KiB) does not fit.

## Large static worlds

A city, a terrain or a level too large to draw whole is a `World`: cells on the ground, each with up to three levels of detail (near, mid,
far) held by chunks that are loaded and freed as a whole (`include/zn/zworld.h`). It is made from glTF by the asset build, and the engine
gives each machine its own budget for it.

**From glTF to `.zworld`.** A rule `"as": "world"` in `zinc.json` turns a glTF or GLB scene, or a `.world.json` that lists several
(`{"scenes": ["streets.glb", "park.gltf"]}`), into the world `<stem>.zworld` beside it, its chunks `<stem>.*.zwc`, the pictures its
materials embed and `<stem>.zworld.json`, the provenance. Nothing else of the scenes (their `.bin` buffers) goes into the packs.

```json
{ "match": "city/city.glb", "as": "world", "cell": 128, "block": 4,
  "targets": { "psp": { "levels": "mid,far", "texture.maxSize": 128 }, "n3ds": { "texture.format": "etc1" } } }
```

| option | default | what it does |
| --- | --- | --- |
| `cell` | 128 | metres of a cell on x and z; a node no wider than a cell goes whole to the cell of its centre, a wider one (a ground) face by face |
| `block` | 4 | a mid chunk holds `block` x `block` cells; a near chunk holds one cell, the far chunk the whole world |
| `region` | 0 | for a very large world, one far chunk per `region` x `region` blocks (`<stem>.f<x>_<z>.far.zwc`) instead of one for the whole world |
| `mid`, `far` | 0.3, 0.08 | the share of triangles meshoptimizer's simplifier keeps for the levels a scene does not give (the cells' borders stay, so they meet) |
| `error` | 0.02 | the mid level's largest error, relative to what is simplified; the far level allows five times it |
| `levels` | `near,mid,far` | the levels this target carries: a console that never draws the near level leaves it out of its packs |
| `texture.*` | the target's profile | the texture importer's options for the embedded pictures (`maxSize`, `format`, `pot`, `mipmaps`) |

A scene gives its own levels with nodes named `<name>_LOD1` and `<name>_LOD2` beside `<name>` (or extras `{"level": "mid"}`); a level it does
not give is simplified from the nearest finer one. In each chunk, one batch per material (the base colour is baked into the vertex colours,
so materials that differ only by it share a batch), its faces ordered by cell, then the upright ones by the 16 compass sectors they face,
then the rest: `World` leaves out the walls that face away from the eye. Textured materials are `wall` batches (their uvs kept on the PSP),
blended ones `open` (drawn last), the others `solid`; a node's textured faces that all look up or down with uvs that follow x and z (a
ground's picture laid over it) are a `top` batch, which the PSP and the 3DS draw without uvs. A material's emissive glows by day and night;
its extras `{"night": "night/windows.png"}` (a picture beside the scene, imported by its own rule) replace its picture at night and
`{"glow": "night"}` lights its emissive only at night. A node's extras `{"reach": 1100}` (metres to its far level) or `{"reach": [450, 1100]}`
(to its mid and to its far level) make it a landmark: a cell and chunks of its own (`<stem>.l<n>.<level>.zwc`) that change level at those
distances rather than the view's. A node's extras `{"id": "<authoring id>"}` names it in the provenance:

```json
{"version": 1, "world": "city.zworld", "cell": 128, "origin": [x0, z0], "block": 4, "cells": 768,
 "sources": [{"id": "tower", "node": "Tower", "file": "city/city.glb", "level": 0, "in": [[cell, level, "city.c12.near.zwc", batch], ...]}]}
```

From Blender: export the static part of a scene, one GLB per world, with each object's authoring id in its custom property `id` (the glTF
exporter writes it into the node's extras), and name the rule after it. `examples/tokyo/tools/city-world.py` writes Pocket Tokyo's own world
from its pack, keeping the levels and sectors Pocket Tokyo's cook made.

**What each machine does with it.** `new World(asset)` takes the defaults of the machine it runs on, `defaults3D()` (zinc:sys `platform()`,
or `ZINC_3D_PROFILE=psp` to try a console's on a desktop; `ZINC_3D_BUDGET` another triangle budget): the reaches, the triangle budget, the
sectors and the idle seconds; `world.serve()` reads the chunks `select()` asked for within `readMs` and frees the unused ones. The haze, the
frame rate, the night and the sky are the program's to apply from `world.defaults`. A program changes only what it wants, on the World or
on the defaults it passes (`new World(asset, d)`):

| profile | near reach | mid reach | budget | haze start, end | fps | night | sky dome | chunk idle | read ms | near slots |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| desktop (and any profile not below) | 600 m | 2000 m | 400000 | 2500, 5800 m | 60 | yes | yes | 0 (kept) | 4 | no limit |
| vita | 300 m | 1300 m | 40000 | 1600, 5800 m | 60 | yes | yes | 0 (kept) | 4 | no limit |
| n3ds | 600 m | 2400 m | 60000 | 1200, 5800 m | 30 | yes | no | 4 s | 6 | 40 |
| psp | 600 m | 1600 m | 42000 | 1200, 5800 m | 30 | yes | no | 4 s | 6 | no limit |
| rpi1 | 300 m | 900 m | 12000 | 600, 3000 m | 30 | no | no | 4 s | 6 | no limit |

`zinc.json`'s `"3d"` changes these numbers without touching the program: a field at the top applies on every machine, a field under a
profile's name (`psp`, `n3ds`, `vita`, `rpi1`, `desktop`, or the platform's own name, `macos`) on that one, after the top's:

```json
"3d": { "budget": 300000, "psp": { "budget": 30000, "midReach": 1400 }, "n3ds": { "slots": 32, "sectors": false } }
```

The fields are those of `Defaults3D`: `nearReach`, `midReach`, `budget`, `fogStart`, `fogEnd`, `fps`, `idle`, `readMs`, `slots` (numbers) and
`sectors`, `night`, `dome` (`true` or `false`); another name is an error that lists them. They are compiled into the program (the module
`zinc:3d/config`), so every engine reads them, the interpreter, a compiled program, QuickJS and a console's pack alike; `ZINC_3D_BUDGET` still
wins for a try.

**Streaming the finest level.** `world.slots` (the defaults' `slots`) caps the chunks of level 0 loaded at once, as Pocket Tokyo's 40 slots:
the nearest cells take them, those behind the eye counted 2.2 times farther, and a loaded chunk gives its slot up only to one at most 1/1.25
as far; a cell without one shows its mid level. On the 3DS the near level lives on the SD card: an asset group (`assets.groups`) that the
console's pack leaves out becomes `<group>.zpk` in a folder named as the program beside it (`tools/console-demos`: `3ds/tokyo.3dsx` and
`3ds/tokyo/near.zpk`), read by a thread ahead of the frames: `load(k)` answers -2 while a chunk or its pictures are on their way, and a
streamed chunk's pictures are freed with the last chunk that draws them.

They are Pocket Tokyo's numbers (`docs/reports/tokyo-per-device.md` has the measurements). The PSP draws a world in two depth passes and
one light per sector, its `clut8` pictures with their day and night palettes mixed by `setNight`, and the sun's shadows (`world.shadows`) in the
top bit of the ground pictures' indices (a ground picture of at most 128 colours, `"colors": 128`); the 3DS in vertex programs per kind of
surface with the sun's shadows; the Vita with its own vertex layout (`docs/reports/pocket3d-techniques.md`); the levels and picture sizes a
console carries are the asset rule's `targets`. Both shadow renderers sweep the heights (Pocket Tokyo's height-grid sweep, a few rows a
frame) when the light has turned by a degree; `clearShadows()` frees the heights.

## Limits and follow-ups

- lighting uses the model matrix's 3x3 for normals (exact for rotations and uniform scale only); back faces of
  double-sided materials are lit with the front normal;
- no transparency, fog, mipmapping or texture filtering (nearest texel); no shadows;
