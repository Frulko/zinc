# Onboarding benchmark: how leading products teach inside the product

Date: 2026-10-22. Method: web search and page fetches. Most product detail comes from third-party teardowns, so each claim is marked **[official]** (product docs), **[teardown]** (secondary write-up) or **[unverified]**. Nothing was tried hands-on. Several results mixed old and new versions; those are called out.

Context: Atelier already has the language card, the 10-step spotlight tour (replayable), a start view with examples by style, a four-style New sketch picker, Help links, error codes that open an explanation, five languages, and a CLI welcome and `zinc tour`. This report only covers what is missing: a checklist, in-app help search, offline docs, "what's new", a sample project that teaches by itself, and an activation measure.

## Products

**VS Code** [official]. Extensions contribute *walkthroughs*: a multi-step checklist shown on the Get Started page, each step with an action button and an image. The UX guidelines say: do not add too many steps, do not add several walkthroughs unless needed, give each step a verb-led action, use theme-aware SVGs. Completion is driven by events declared in the manifest (not confirmed on the guidelines page; see the contribution points reference). The 2017 "Interactive Playground" let users try multi-cursor, rename, folding in a scratch file with no project [teardown, old]. Profiles and Settings Sync are doc topics I could not confirm in detail. Remarkable: the checklist is data (JSON), not code, so any extension can add one. https://code.visualstudio.com/api/ux-guidelines/walkthroughs , https://code.visualstudio.com/api/references/contribution-points

**Zed** [source code, mixed versions]. Welcome page when opened with no folder: open folder, clone, docs, pick a base keymap, theme toggle, an edit-prediction opt-in; it vanishes once you open something and can be reopened from the command palette. Settings import from VS Code is a command. I found no in-app "what's new" and no telemetry step (not confirmed). Remarkable: onboarding is one page of choices that change the product, not a tour. https://zed.dev/docs/migrate/vs-code.html , https://git.secluded.site/zed/blob/v0.184.8/crates/welcome/src/welcome.rs?raw=1

**Cursor** [teardown, weak sources]. First launch offers one-click import of VS Code settings, keybindings, themes and extensions (also later in Settings), plus a data-sharing / privacy-mode choice. Remarkable: it removes the cost of switching. Not relevant to Zinc users who have no previous editor; the lesson is "ask only questions whose answer changes something". https://hyperskill.org/learn/step/53277

**Figma** [teardown]. Loads interactive example files ("Figma Basics", "FigJam Basics") into the workspace on first login: users edit real layers instead of reading docs. A modal offers a tour, then a few tooltips (import, invite). Templates and community files fight the blank canvas. https://goodux.appcues.com/blog/figmas-animated-onboarding-flow , https://supademo.com/user-flow-examples/figma

**Notion** [teardown]. A short survey picks templates; a "Getting Started" page is itself a Notion page you edit while reading (learn by doing); a templates gallery avoids the blank page. One user comment warns that both a blank page and a full template are daunting and suggests a minimal starter with 2 or 3 blocks (opinion). https://candu.ai/blog/how-notion-crafts-a-personalized-onboarding-experience-6-lessons-to-guide-new-users , https://onboardme.substack.com/p/how-notion-solved-the-blank-page-product-strategy-deepdive

**Linear** [teardown]. No tours or tooltips: a short flow with one input per step (theme/UI style, command menu shown before any action, connect GitHub, invite). Claimed time from signup to first issue about one minute (vendor estimate). Sources disagree on step order and the flow may have changed. https://www.candu.ai/blog/linear-onboarding-teardown , https://supademo.com/user-flow-examples/linear

**Raycast** [official + teardown]. A few steps at install: pick the global hotkey, import the old setup (v2). The Quickstart in the manual is a short list of first wins: search an app, make a snippet, install an extension, chat. I found no teardown of the screens; the one flow gallery needs sign-up. A claim that v2 left beta in August 2026 is **[unverified]**. https://manual.raycast.com/quickstart

**Warp** [official, conflicting guides]. Official quickstart: a terminal is ready at launch, an account is optional (about 10 minutes of guided steps). Older docs and third-party guides say login is required and the survey is skippable: sources conflict. Lesson: the first screen is the working tool. https://docs.warp.dev/getting-started/quickstart

**Obsidian** [official + forum]. The old separate Help vault was replaced (2022 changelog) by a *sandbox vault*: a disposable vault opened from the Help icon or a command, so users can try things without touching their notes; help lives online at obsidian.md/help and the Help repo is public. Forum users complained the bundled help went stale. Lesson: a sandbox is safe to break; bundled docs must be versioned with the app. https://obsidian.md/help/sandbox , https://forum.obsidian.md/t/when-i-start-obsidian-the-help-vault-opens/22628

**Blender** [official, 2.8 to 3.3 manuals]. A splash screen on every start; on the very first start its lower half is a Quick Setup (steps not confirmed in what I read). The splash also holds New File, Recent, Open, Recover Last Session and links, and is reachable again from the Blender icon. Esc or a click outside dismisses it. https://docs.blender.org/manual/en/2.90/interface/splash.html

**Duolingo** [teardown]. A first lesson before account creation; a few questions (goal) personalize; sign-up is prompted later and stays optional; an early score is the first win. One LinkedIn claim about timing is weak. https://goodux.appcues.com/blog/duolingo-user-onboarding , https://www.appcues.com/blog/the-10-best-user-onboarding-experiences

**Canva** [teardown]. Asks "what will you use it for" (personal, work, teaching, nonprofit) and shows templates, no blank canvas. Activation: edit a template and export. Canva's own help says you can answer "personal" if unsure. https://goodux.appcues.com/blog/canvas-user-tailored-onboarding-flow , https://supademo.com/user-flow-examples/canva

**Arduino IDE** (added; closest audience to Zinc) [official]. Built-in examples under File > Examples, from Bare Minimum and Blink up; each is a real runnable sketch. https://docs.arduino.cc/built-in-examples/

## Patterns and evidence

- **Tours help little on their own.** NN/g tested 4 apps with deck-of-cards tutorials (70 users): readers did not do better; a secondary write-up quotes 4.92 vs 5.49 ease and 91% vs 94% success (check the article for exact figures). NN/g advice: onboarding suits apps that need user info or have unfamiliar interactions; keep it short, show what is unfamiliar. Atelier's tour is replayable and skippable; keep it, but do not grow it. https://www.nngroup.com/articles/mobile-tutorials/
- **Learn by doing beats explaining.** Figma example files, Notion's editable Getting Started, Arduino examples, Canva "edit a template", Duolingo first lesson all put a real artifact in the user's hands. Evidence is teardown-level, not controlled studies.
- **Empty states should teach.** NN/g: empty states are common in complex apps during onboarding and can build confidence, improve learnability and start key tasks. Full text not read. https://www.nngroup.com/articles/empty-state-interface-design/
- **Checklists.** Endowed progress (Nunes and Drezé 2006): a card with 2 of 10 stamps pre-filled was completed more often (one summary says 82% more) than an 8-stamp blank card. For onboarding, "4 to 7 items" is a practitioner rule of thumb with no study behind it, and fake progress can look manipulative. VS Code advises few steps and one walkthrough. I found no direct evidence on Zeigarnik. https://ideas.repec.org/a/oup/jconrs/v32y2006i4p504-512.html
- **Progressive disclosure.** Defer advanced options to a secondary screen so the primary ones are easy to learn (NN/g, from 1995); one secondary source says empirical evidence is thin [unverified quote]. https://www.nngroup.com/videos/progressive-disclosure/
- **Ask few questions, and only ones that change something.** Canva use-case, Notion goal, Linear UI style, Zed keymap, Raycast hotkey. All are skippable or defaultable.
- **Sandbox and sample content.** Obsidian sandbox, Figma example files: safe to break, so users try. Risk: stale bundled content (Obsidian forum).
- **"What's new".** VS Code opens release notes after an update, controlled by `update.showReleaseNotes` (third-party source; setting name should be checked in the VS Code settings reference). Users complain when it re-opens on every launch. Rule: show once per version, never block, one setting to turn off. I found nothing on Zed.
- **Measuring activation without invasive telemetry.** Homebrew: a notice before anything is sent, opt out with a command or env var; its default is disputed (check https://docs.brew.sh/Analytics). Telemetry is contested for GDPR reasons (one developer's view, not a legal finding). I found no source on a local-only activation metric: the idea below is my own proposal, not an established pattern. Activation events named in teardowns: Canva "edit a template and export", Figma "first real layout".
- **Accessible tours.** No standard found for spotlight tours. Evidence by example: a Drupal Tour review found focus left on the trigger so keyboard users could not advance and state attributes did not update; UserGuiding says a tour step takes focus and keeps it inside until the user advances or dismisses. General rule: move focus into the step, return it on close, make Next, Back and Skip reachable by keyboard, honour reduced motion (Framer's spotlight component does for camera moves). Which WCAG criteria apply to overlays is **[unverified]**. https://cloudscape.design/foundation/core-principles/accessibility/focus-management-principles/
- **Localising onboarding.** Rules of thumb from vendors (marketing, not standards): budget about 35% more width for German and Finnish, give translators context not bare strings, localise screenshots, version the source so an English edit flags the translation, follow the app's chosen language not the system's. https://translated.com/resources/saas-in-app-tooltips-localization

## Ideas for Zinc (ranked: value for the users, against effort)

1. **Teaching sample sketch ("Your first sketch", open in a sandbox copy).** Who: Figma example files, Notion Getting Started, Arduino examples, Obsidian sandbox. An example whose comments are the lesson, with 3 or 4 marked "change this number" places and a live result; opens as a copy so nothing can break. Atelier: one more entry in the start view examples, copied to a temp project, with a banner that links back. The text is plain comments, localised with the rest. Value: high, effort: low. Fits non-developers best.
2. **First-steps checklist on the start view, 4 or 5 items, first one pre-ticked.** Who: VS Code walkthroughs, Linear/Notion style checklists. Items: run an example, change something and see it re-run, make a new sketch, read an error explanation, export or save. Ticks come from events Atelier already sees (run, edit, new, error opened); stored in local settings; dismissible; "Skip all". Atelier: a small list component and 5 flags. Value: high, effort: low to medium. Keep it to one list (VS Code advice).
3. **In-app help search (command palette style) over bundled docs and error codes.** Who: Raycast, VS Code command palette, Linear command menu. One shortcut, one box: searches lesson titles, doc headings, `zinc explain` codes and Atelier commands. Atelier: build a small index at build time from `docs/` and the explain texts; match by simple scoring. Value: high, effort: medium. Also gives the CLI a `zinc help <words>`.
4. **Offline docs bundled with the app, version-stamped.** Who: Obsidian (and its stale-help complaints), Arduino built-in examples. Ship the lessons and guides in the app so the first hour works without a network (schools, makers on weak wifi). Needs a docs build step and a "docs version" label; rebuild per release so they cannot go stale. Value: high for the audience, effort: medium. It is the base of idea 3.
5. **Empty states that teach.** Who: NN/g guidance, Notion, Figma. Every empty panel (no sketch open, empty console, no recent files, no errors) gets one sentence and one button ("Open an example", "Run to see output here"). Atelier: copy and a button per panel, in five languages. Value: medium to high, effort: low.
6. **"What's new" once per version.** Who: VS Code release notes after update. After an update, a small non-modal card on the start view with 3 to 5 plain lines taken from `CHANGELOG.md` `[Unreleased]`-turned-release text (already written for users), shown once, with a setting to disable. CLI: `zinc --version` prints a line, `zinc changelog` prints it. Atelier: read the version of the last run from settings; embed the section at build time. Value: medium, effort: low (the changelog already exists).
7. **One-question personalisation, skippable: "What do you want to make?" (drawing, scene, canvas, interface, device).** Who: Canva, Notion survey, Zed keymap. The answer sorts the start view examples and picks the default style of New sketch; no extra screens. Atelier: reuses the style groups already there. Value: medium, effort: low. Caution: keep it one question and always skippable; the existing four-style picker may already cover most of this, so do it only if the start view still feels long.
8. **Local-only activation measure (opt-in, exportable).** Who: no product found doing exactly this; closest is Homebrew's notice-before-send model, here without sending. Atelier keeps a local counter file: time from first launch to first run, first edit and re-run, first error opened, first save, with no id and no network. A "Share my numbers" button writes a small JSON the user can attach to an issue, and the owner can run it in workshops or classes. Value: medium (lets you find where classes get stuck), effort: low to medium. This is my proposal; privacy review needed.
9. **Tour accessibility pass.** Who: UserGuiding and Cloudscape guidance, Drupal Tour review as the anti-example. Check on the existing tour: focus moves into each step and returns on close, Next/Back/Skip by keyboard, Esc skips, step text announced, reduced-motion respected, text not clipped in German. Value: medium (needed for schools), effort: low. Run it against the five languages.
10. **First-run splash with recent and recover (Blender).** Who: Blender splash (reopen from an icon), Zed (welcome closes when you open something). Partly covered by the start view; the missing piece is "Recover last session" and a Help menu entry that reopens it. Value: low to medium, effort: low.
11. **CLI parity: `zinc tour` ends with the same first steps, and `zinc new` ends by printing one next command.** Who: Raycast Quickstart, Warp quickstart (working tool at once). Value: low to medium, effort: low.
12. **Import step (Cursor, Raycast).** Not recommended now: Zinc users mostly have no previous editor. Revisit when users of Processing or Arduino projects need an import of sketches.

Not recommended: more tour steps (NN/g found tutorials do not raise success), forced account creation (Duolingo and Warp both let you start first), a second checklist or walkthrough (VS Code advises against it).

## Could not verify

Raycast and Linear current flows (teardowns only, and they disagree); Blender Quick Setup steps (only 2.8 to 3.3 manuals read); the exact Zed welcome page today; Cursor first launch (secondary sources only); Warp login requirement (conflicting); Homebrew's current analytics default; the VS Code `update.showReleaseNotes` details and the walkthrough completion-event schema; WCAG criteria for spotlight overlays; any controlled study of onboarding checklists (only the endowed progress paper).
