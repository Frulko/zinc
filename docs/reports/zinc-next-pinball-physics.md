# Shared pinball physics and cabinet refresh — 2026-10-25

Owner request: make both pinballs more predictable and lively using Space Cadet as a reference, share improvements across demos, use proven physics libraries, then improve UI and assets.

## Engine and scope

`examples/pinball-kit` now owns the Box2D 3.1.1 adapter, Jolt 5.6.0 adapter, table schema/loader, collision/render geometry, calibration, fixed clock and cosmetic recoil. Nova Patrol and its DS view share Box2D; the 3D game and editor share Jolt. Existing vendored plugins and licences are reused. The game's rules, input, scoring and rendering remain outside the kit. No handwritten collision solver is shipped by the live demos.

Reference: Space Cadet's [pb.cpp](https://github.com/k4zmu2a/SpaceCadetPinball/blob/master/SpaceCadetPinball/pb.cpp) limits ball travel between collision updates; [TFlipperEdge.cpp](https://github.com/k4zmu2a/SpaceCadetPinball/blob/master/SpaceCadetPinball/TFlipperEdge.cpp) transfers energy from a moving surface. We adopt the half-radius relative-travel bound and passive held flippers. Raw original gravity values are not a verified tuning preset: game data and units matter. Microsoft [says it cannot publish the original source](https://devblogs.microsoft.com/oldnewthing/20181221-00/?p=100535); the referenced project is a community decompilation. No original game assets are copied.

## Physics corrections

- Box2D owns 2D contacts, continuous collision, friction, spin and multiball. Kinematic flippers stop explicitly in a held pose: Box2D's target-transform function can return without clearing a previous velocity. Plunger motion retains the final interval's impulse. Tests cover both.
- 2D gravity changes from 58 to about 31.2 in/s², matching a solid sphere's rolling acceleration on a 6.5° board. The common physical gravity is 981 cm/s² and speed cap 700 cm/s. The 2D coil cap changes from 44 to about 31.4 rad/s and the full plunger-tip speed from 230 to about 189 in/s. 3D table-authored coil and material values remain data.
- Jolt's separating contacts are no longer converted to approaching ones by `abs(speed)`. Relative-travel subdivision includes moving flippers and all live balls; duplicate contact reports within one outer step produce one touch per ball/part.
- Ramp layers use separate Box2D worlds; a portal transfers the ball after all worlds have stepped, avoiding a double advance. The target bank moves against the wall; the ramp underside lip slopes instead of forming a horizontal resting pocket.
- All game loops consume rendering delta through `FixedClock`; physics stays fixed-step and ball rendering interpolates. Catch-up is capped at 100 ms after a stall. Tests prove equal physical positions at 30/60/120 rendering Hz and preserve time with uneven frame deltas.

Calibration probes, before → after: left-flipper peak shot speeds at distances 1.2/1.8/2.4/2.9 in from its pivot are 84.5/120.9/187.4/164.4 → 49.9/78.7/127.3/120.4 in/s. A held flipper keeps the dropped ball at approximately (6.3, 35.8), effectively still after three seconds. A 50 in/s ramp shot falls short; 60 in/s reaches the wire. The final ten-minute autopilot soak reports no stuck ball and ends at score 273200. These are calibration checks, not a human assessment of fun or fairness.

## 0.2.3: complete-refresh profiling and coherency cost

The owner reports that 0.2.2 remains highly variable in flat and stereo modes, and requests measured 60 FPS rather than another average-cost estimate. The previous TypeScript callback timers excluded bottom-window hashing/replay and synchronization, so their3 ms figure did not describe a complete refresh. Replaced the extra physics callback timer with native phase marks and a buffered per-refresh capture reusable by all 3DS demos. It combines both eye callbacks with the bottom window, records CPU time excluding explicit GPU/vblank wait, native replay/validation/upload/submit costs, previous GPU queue time, actual vblank deltas, software fallbacks, quads and existing runtime allocation counters. CSV rows are a 3600-refresh ring; recording itself neither allocates nor writes to SD per refresh. Exit dumps the latest minute. The portable capture/gate regression tests eye aggregation, allocation deltas, rollover and rejection of stalls.

A concrete GPU coherency problem was found: `C3D_FrameEnd(0)` asks citro3d to flush its entire linear heap every frame, even though this backend explicitly flushes changed textures/atlases and used vertices. Changed it to `GX_CMDLIST_FLUSH`, retaining all explicit buffer flushes and letting citro3d flush the command list. The 3D backend's static/dynamic vertices, indices and textures also already have explicit flushes. [Primary citro3d source](https://github.com/devkitPro/citro3d/blob/master/source/renderqueue.c) documents the global flush in `C3D_FrameEnd` and the queue timing. This is a strong physical-device cost candidate, not a measured physical improvement; Azahar does not establish cache-maintenance cost.

Additional work with unchanged solver/calibration: Box2D step, moved-body snapshot and contact snapshot cross the native bridge once instead of three times; a single packed result replaces two arrays. Legacy native operations remain available. New `physics2d_bulk` compares 1200 steps against the old protocol: every state/contact field matches exactly (handle IDs normalized), runtime allocations 7240→6016. Existing drop replay and 10,000 fast collision shots pass, including interpreter/AOT/QuickJS goldens. Fixed lamp hot contours are projected once beside their outer contours, removing per-eye camera projection work and temporary geometry arrays. Kept windows skip command hashing. The requested FPS readout moves 6 pixels right; bottom-screen capture checked visually. No additional reduction of the 240 Hz base step, CCD, gravity, travel subdivision or effects budget.

The source is explicitly emulator in the generated reports; physical 60 FPS remains unproven. CSV/JSON artifacts: `build/n3ds-pinball-023-{flat,stereo}.csv` and corresponding `-report.json`. Startup is excluded, not claimed solved.

Tests passing: `physics2d`, `physics2d_bulk`, `pinball_core`, `pinball`, `n3ds_demos`, `n3ds_pinball_multiball`, `n3ds_frame_profile`, plus real 3DS HAL emulator captures. ## 0.2.4: physical trace identifies a physics work spiral

The owner returned a real 0.2.3 Old3DS capture. Preserved before installation in `build/n3ds-pinball-physical-023/{zinc-frames.csv,zinc.log,report.json}`. Latest 3600 stereo refreshes: 41.11 FPS, 1639 missed refreshes/vblanks, physics median/p99/max 2.572/47.263/96.940 ms, complete CPU 9.450/55.311/105.911 ms. GPU queue maximum 6.425 ms, zero software surfaces and zero texture uploads. Runtime allocation p99/max 622/1100. This confirms CPU rules/physics spikes, not GPU fallback. The global `2*fastest+surfaceSpeed` bound caused up to 9 adapter/native steps per 240 Hz interval for a lone fast ball, including when the flipper/plunger was on the opposite end of the board; a slow refresh then asked the unchanged fixed clock to catch up more work.

The 2D adapter now relies on Box2D bullet CCD for static/kinematic free-flight contacts. It retains half-radius travel subdivision only for nearby active same-layer ball pairs, and nearby slow balls hit by a moving flipper or plunger. Proximity bounds include maximum ball travel, and the full flipper swept enclosing radius. Slow-ball eligibility uses a lower speed bound accounting for gravity/damping. This is step selection; all contact detection/response remains Box2D. The pinned 3.1.1 headers explicitly exclude bullet/bullet CCD, and `vendor/box2d/src/solver.c:626` activates CCD based on the dynamic body's own motion. Thus neither the ball-pair nor stationary-ball/mechanism guard was removed. [Box2D primary simulation documentation](https://box2d.org/documentation/md_simulation.html) corroborates the bullet exclusion; code behavior is checked against the pinned local version.

Removed unused legacy tangent edges from the flipper adapter: only the render tip changes now, while the native tapered shape/material stays identical. Base clock, gravity, restitution, friction, speed limit and catch-up policy are unchanged; no time is silently dropped to inflate FPS. Added native `physics_steps` to refresh captures/reporting; old CSV files remain compatible. Tests assert fast free flight far from a moving flipper uses one adapter step, opposing fast balls still collide, stationary balls launch from a moving flipper at 240/60 Hz, the held cradle remains stable and the plunger's final stroke still transfers energy. The bumper speed-cap test starts at contact to isolate impulse clamping from CCD's deferred contact reporting.

The changed trajectory reaches the kicker-hole random-ejection branch in the desktop pixel proof. That exposed independent engine Math.random streams rather than a numeric physics divergence (first differing replay frame 232). Game and effects now use separate instances of the cabinet art's existing LCG, shared via pinball-kit/random.ts. Its initial sequence is asserted in core tests; interpreter/QuickJS image parity now passes with no widened pixel tolerance. Updated only the 2D pinball image and 3 DS pinball frame hashes; other DS demos and frozen language outputs stay unchanged.
