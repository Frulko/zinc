# Onboarding through docs and the browser: benchmark (2026-10-22)

How the best docs and learning sites teach a newcomer, what runs in the page, and what Zinc should copy. Method: live fetches and searches on 2026-10-22. Where a page could not be read or a number comes from a third party, it says so ("not verified"). Sites that rate-limited or returned 404 (hello-algo.com, exercism.org/how-it-works) are described from search results and general knowledge, marked as such.

## 1. The sites

**Svelte tutorial** (https://svelte.dev/tutorial, formerly learn.svelte.dev). Four parts (Basic Svelte, Advanced Svelte, Basic SvelteKit, Advanced SvelteKit), each a sidebar of short lessons. Lesson text on one side, a real editor with a file tree on the other, a "Solve" button top right that fills in the answer ("type it yourself" is advised), a "show text / show editor" toggle for small screens. The SvelteKit part runs on StackBlitz WebContainers (a Node in the tab), because SvelteKit needs a server. Remarkable: the exercise is the lesson; no setup, no login; the solution is one click away so nobody stays stuck. StackBlitz then packaged the pattern as TutorialKit (https://tutorialkit.dev), an Astro-based kit for lessons (details of the kit not verified, the page was thin).

**A Tour of Go** (https://go.dev/tour). Short pages, each with a runnable, editable program and a Run button; code is sent to the Go Playground service (compile and run on a server, fixed fake clock, no network). The same tour ships as a local program (`go install golang.org/x/website/tour@latest`) that runs samples on the machine. Remarkable: one tiny idea per page, translations exist (community), and the offline variant for classrooms with bad internet.

**TypeScript Playground and Handbook** (https://www.typescriptlang.org/play, /docs/handbook/). The Playground is Monaco plus the real compiler in the page: shows JS output, .d.ts, errors, and the whole program lives in the URL hash, so a bug report or a teaching example is one link. It has an Examples list. The Handbook is read top to bottom; reference files are separate and unordered (a Diátaxis-like split). Remarkable: share-by-URL, and the compiler itself is the runtime.

**React docs** (https://react.dev/learn). Quick Start covers "80% of daily React" in ten short steps; nearly every code block is a live Sandpack (multi-file, editable, with a Reset and a Fork button), with line highlights per step and diagrams for state flow. Then a tic-tac-toe tutorial, "Thinking in React" (a design method on paper first), and Challenges at the end of each page (small tasks with hidden solutions you reveal on demand). Remarkable: practice sits at the end of each concept page, so the docs and the course are one thing; `/llms.txt` is published for AI tools.

**Vue docs** (https://vuejs.org/tutorial, /examples, https://play.vuejs.org). Tutorial in the browser with a step list and a "Show me" button; a Playground whose state is in the URL; a toggle between two API styles in the whole docs. Translations are separate community repos (for instance vuejs-translations/docs-zh-cn): they mirror the English repo, maintainers sync upstream changes by hand or with helper scripts, and untranslated paragraphs carry a `<!-- TODO: translation -->` marker to search for. Process is manual and human-led, no bot visible on the repo page.

**MDN Learn** (https://developer.mozilla.org/en-US/docs/Learn_web_development). Long-form beginner path with assessments at the end of each module and "Try it" live examples on reference pages. Translations live in a separate repo (mdn/translated-content) with seven active locales (fr, ja, ko, pt-BR, ru, es, zh); only locales with a community team that reviews PRs are accepted, the others were retired in 2021 (https://hacks.mozilla.org/2021/03/mdn-localization-in-march-tier-1-locales-unfrozen-and-future-plans/). Lesson: translation needs owners, not just files; an untended translation is worse than none.

**Tailwind docs** (https://tailwindcss.com/docs). One page per concern; installation pages with numbered steps per framework and tabbed commands; every utility page shows the rendered result above the HTML; search with `/` shortcut. Remarkable: "the answer in the first screen" and a visual result next to every snippet (not an editor, a rendering).

**Stripe docs** (https://docs.stripe.com). Code beside prose in a two-column layout, language switcher that sticks, copy-as-Markdown versions of pages (`.md` suffix on any URL), a terminal reader (`stripe docs` in the CLI), and published agent skills and an agent-oriented sandbox with no signup (verified on the live page, in French). Remarkable: the docs are treated as an interface for AI coding agents as much as for people.

**Exercism** (https://exercism.org). Two modes: an in-browser editor, or the CLI (`exercism download`, `exercism test`, `exercism submit`). Each exercise ships a README, a stub and tests; automated checks run on submit; optional volunteer mentoring; after passing you compare solutions with others. Remarkable: tests are the exercise, and a human mentor answers the learner's own code. (From search results; the how-it-works page returned 404.)

**freeCodeCamp** (https://www.freecodecamp.org/learn). Step-by-step projects where each step is a small edit checked by tests running in the browser (community answer: Chai assertions in a web worker; verify in the repo). Hint button, "Run the tests", ticks. Remarkable: the checker gives a message about the specific missing thing, which makes a project feel like a conversation. A long certification path gives motivation.

**Codecademy** (https://www.codecademy.com). Lesson text left, editor middle, output right, "Run" then a checkpoint with feedback; paid parts hold projects and AI help. Not re-fetched; known pattern. Takeaway: a visible progress bar and syllabus per course.

**The Coding Train** (https://thecodingtrain.com). Long, friendly videos that build a thing live with p5.js; each video links to the p5 web editor sketch to open and change. Remarkable: tone (mistakes shown on camera), and every video has runnable code. Fits artists and makers directly.

**Rust by Example** (https://doc.rust-lang.org/rust-by-example/). An mdBook: every code block has a play button that sends it to the Rust Playground, and blocks can be edited in place; keyboard shortcuts, six themes, print page, "suggest an edit". Remarkable: it is only a book plus a playground service; costs the project almost nothing.

**Kotlin Koans / Kotlin Playground** (https://play.kotlinlang.org). Koans are exercises with tests in a browser or IDE; the embeddable `kotlin-playground` script turns any code block into a runnable one (compiles on JetBrains servers or via Kotlin/Wasm). Not re-fetched. Takeaway: a one-script embed makes every docs page runnable.

**Hello Algorithm** (https://www.hello-algo.com). Open-source illustrated book with animated diagrams, code in about ten languages with a tab switcher, and community translations (en, zh, ja, ...). Page returned 429, so this is from memory; check before quoting. Takeaway: pictures and animation for ideas, one translatable source.

**Docs frameworks**
- Starlight (https://starlight.astro.build): the framework Zinc's Astro site could lean on: built-in search, i18n with fallbacks, dark mode, MDX, frontmatter validation. Versioning is not built in (page does not mention it).
- Pagefind (https://pagefind.app): static search, no server; the live page claims a 10,000-page site is searchable with under 300 kB total download (about 100 kB typical), multilingual out of the box. Starlight uses it by default.
- Docusaurus: versioning and i18n built in, Algolia DocSearch plug-in, community Ask-AI add-ons (search did not return details; not verified).
- Mintlify (https://mintlify.com): hosts `/llms.txt` and `/llms-full.txt` automatically, a generated MCP server at `/mcp`, and a paid in-page assistant with citations (third-party description).
- llms.txt (https://llmstxt.org): one Markdown file at the site root: an H1 with the project name (the only required part), a blockquote summary, H2 sections of links with notes, an `Optional` section; plus a `.md` copy of each page, and `rel="alternate" type="text/markdown"` discovery. OpenAI, Anthropic and Google publish one; React docs link theirs from the Quick Start.

## 2. Patterns that the best ones share

1. Code is runnable in place; the lesson is the exercise (Svelte, React, Vue, Rust by Example).
2. The state of an example is a link (TS Playground, Vue Playground): the unit of help, bug report and class handout.
3. A checker with a specific message (freeCodeCamp, Exercism), and a solution one click away (Svelte).
4. Small, one idea per page; a visible result next to each snippet (Tailwind).
5. An offline path for classrooms (Go tour binary, Exercism CLI).
6. Docs written for two readers: people and AI agents (Stripe, Mintlify, React llms.txt).
7. Translations have an owner and a sync marker (Vue TODO markers, MDN tiers).

## 3. Running code in the page: options for Zinc

What Zinc already has (verified in the repo):
- `tools/build-wasm` builds `vm.wasm` (WASI) and `vm-web.wasm` (reactor, `zn_run(zbc, len)` plus one graphics import) with the pinned zig; no emscripten.
- `targets/wasm/glue/` runs it in a worker, draws zinc:gfx on an OffscreenCanvas, and uses `Atomics.wait` for the frame loop, so the page must be cross-origin isolated (COOP/COEP).
- `site/public/play/` already ships two precompiled demos (breakout, bouncing-ball) with a `coi-sw.js` service worker that adds COOP/COEP on GitHub Pages. `vm.wasm` there is 5.8 MB raw, about 1.6 MB gzipped (measured with gzip -c). It runs `.zbc` that was compiled ahead of time on the developer's machine.
- The `web` target (`zinc export --target web`) is different: the app's own JavaScript runs on the browser's engine, no COOP/COEP, 100 to 120 kB Brotli for a dashboard app; but the TypeScript is bundled by esbuild at export time, on the machine, not in the page.

The gap for a lesson page: the learner edits source, so something must turn Zinc/TSX text into ZBC (or into JS) in the page. Today the compiler (frontend, tc, IR, ZBC writer) is native C++ only. Everything else needed exists.

| Option | What runs | Load cost | Needs | Fit for Zinc |
|---|---|---|---|---|
| A. Precompiled, not editable (what `play/` does) | `vm-web.wasm` runs a `.zbc` built in CI | 1.6 MB gz once, cached; plus a few kB per lesson | COOP/COEP (service worker exists) | Done for 2 demos. Cheap to extend to every lesson sample: "Run" button, no editing. Tested samples already exist. |
| B. Compiler to wasm too (a `zinc-compile.wasm` of frontend + ZBC emit), VM wasm to run | Full edit-run loop, offline, no server | Compiler wasm size unknown: needs a measurement (the VM alone is 5.8 MB raw; a frontend is likely larger; plan for 3 to 8 MB gz, cache it with the service worker) | zig build of `src/frontend`, `src/ir`, `src/zbc` for wasm32-wasi; the stdlib `lib/std` bundled as a virtual file system; no threads needed except for the frame loop | The real playground. How TypeScript, Svelte and Go (via wasm) do it. Medium-large effort. |
| C. Compile on a server (Go Playground, Rust Playground, Kotlin) | Server returns ZBC, page runs it | Tiny page; a server to run, secure and pay for | Hosting, rate limits, an abuse story | Against the project's autonomy; fragile for a volunteer project. Not recommended; at most a fallback. |
| D. Web target in the page (esbuild-wasm or a JS-only path: TSX to JS in the page, run on the browser engine) | JS on the browser's JIT, canvas or DOM | esbuild-wasm is about 10 MB raw by memory (not verified here); or the `zinc` frontend emitting JS only | A JS emit path in wasm | Fastest runtime and no COOP/COEP, but the output must match the engine (one program, many targets is the promise); keep for "export to web" preview, not for lessons. |
| E. StackBlitz WebContainers (Svelte tutorial, TutorialKit) | A Node in the tab; would run `zinc` only if a wasm build of it existed | Heavy (a Node, npm packages) | COOP/COEP, HTTPS, StackBlitz API and terms: commercial production use needs a license (search result, verify), hosted proxy parts | Not suited: Zinc is not Node; and the dependency on a company service conflicts with "proven libraries, no lock-in". |
| F. Sandpack (React docs) | CodeSandbox's in-browser bundler, for JS/React | Bundler fetched from a CDN or self-hosted; size not stated on its docs page | Designed for JS bundling | No: it runs JS frameworks, not Zinc. Useful only for the web target if Zinc code is first compiled to JS. |
| G. Editor widget: CodeMirror 6 vs Monaco | The text box, not the runtime | CodeMirror 6 about 50 to 300 kB tree-shaken; Monaco about 1 to 5 MB (sources disagree, see Sourcegraph and Replit write-ups) | A Zinc/TS grammar | CodeMirror 6, loaded only on pages with a runnable block. A Lezer TypeScript grammar exists; diagnostics could come from option B's checker. |
| H. Local path for classrooms | `zinc dev` serving the lesson (like Go's local tour) | none | an installed zinc | Free once the lesson format exists. |

Browser-side facts to watch: the `Atomics.wait` frame loop needs cross-origin isolation, so embeds in third-party iframes or pages without headers will not run; the service worker trick (`coi-sw.js`) works on GitHub Pages but fails on first load (a reload is needed) and in private windows on some browsers. For lessons, a mode with no SharedArrayBuffer (frame loop yielding with asyncify or a message per frame) would remove the headers problem; estimate effort in a spike. Pyodide (Python in wasm) is the closest public precedent for shipping a whole language runtime to a page: its core is tens of MB and is accepted because the use is educational and cached; Zinc is already smaller.

## 4. Ideas for Zinc, ranked by value against effort

Who: "agent" means a loop agent or session in the repo, "owner" means an outward-facing step only the owner takes (publishing, accounts).

1. **llms.txt, `llms-full.txt` and a `.md` copy of every page.** Value: high, effort: very low (a few hours). Who: agent. Take: an Astro endpoint in `site/src/pages` that walks the docs content map (`site/docs-map.mjs`) and writes `/llms.txt` (H1, blockquote, links per Diátaxis section, an Optional section for reference), `/llms-full.txt`, and `page.md` for each language page; add `<link rel="alternate" type="text/markdown">`; a test that every doc page appears. Also fits zinc's own agents.
2. **Search with Pagefind, plus a check.** Value: high, effort: low (a day). Who: agent. Take: `pagefind` after `astro build`, a search box with `/` shortcut in the layout, one index per language (Pagefind is multilingual), and a check in the site tests that a query for 10 known terms ("gfx", "stage", "useState"...) returns the right page in each language. Closes the "no search check" gap.
3. **"Run" button on every tested lesson sample (option A).** Value: very high, effort: medium (3 to 5 days). Who: agent. Take: the 20 lessons already have tested samples; in the site build, compile each to `.zbc` with `zinc --emit=zbc-bin` (the same command the tests use), copy it to `site/public/play/<lesson>/`, and add one Astro component that mounts the existing glue (`targets/wasm/glue`) in a panel beside the code with a Reset button. Needs the `coi-sw.js` registration and a "needs a recent browser" fallback to the screenshot already in the lesson. No editing yet, but a newcomer sees the program run before installing anything. Honest limit: only programs that use rows `vm-web.wasm` draws (gradients, shadows, polygons, runtime images still warn); pick lessons accordingly and list which ones run.
4. **Shareable "open in the editor" and a copy-as-Markdown/prompt button.** Value: medium, effort: very low. Who: agent. Take: on each code block a Copy button (check if it exists) and a "Copy page for AI" button that fetches the `.md` copy of idea 1 (Stripe, Mintlify do this).
5. **Edit-and-run playground (option B).** Value: very high, effort: large (2 to 4 weeks, with a measurement spike first). Who: agent, one task chain. Take: (a) spike: build `src/frontend`, `src/ir`, `src/zbc` for wasm32-wasi with `tools/build-wasm`, measure raw and gzip size and the compile time of a 50-line program; (b) bundle `lib/std` and `zinc.d.ts` as a virtual FS; (c) CodeMirror 6 with a TS grammar and the checker's diagnostics (Zinc's errors have codes and `zinc explain` texts: link them); (d) state in the URL hash so a link is a program (TS and Vue playgrounds); (e) a `/play/` page and the lesson blocks use it. Decide in the spike whether to drop the SharedArrayBuffer need for the frame loop. Owner: only the decision to publish the site.
6. **Lessons turn into exercises with checks.** Value: high, effort: medium once idea 5 exists. Who: agent for the format, owner for the pedagogy review. Take: add to each lesson an optional `exercise` front-matter (starter code, a test program run in the page as in freeCodeCamp: the test is a Zinc function that prints PASS lines; a failure prints one specific message), a hint, and a "Show solution" button (Svelte's Solve). Start with 5 lessons. The same files can be used offline: `zinc test lessons/<n>` (Exercism's CLI idea; the repo already has `zinc test`), so a classroom without internet works.
7. **Translation tracking like Vue's, automated.** Value: medium to high (five languages already), effort: low to medium. Who: agent. Take: extend the existing translation check: store in each translated page's front-matter the English source commit (`sourceHash`), report pages where the English page changed since; show a banner "this page may be out of date, see the English page" generated from that (MDN tiers lesson: a stale translation should say so); keep the TODO-marker convention from Vue for partial pages. Weblate/Crowdin: do not adopt now; Weblate's Markdown support is described as still under development and it makes the tool, not Git, the source of truth (third-party report, not verified); revisit if non-developer translators arrive.
8. **Videos and GIFs, small and honest.** Value: medium, effort: medium. Who: owner records or approves; agent produces silent captures. Take: `ZINC_SHOT`/`zinc capture` already make frames: generate short looping animated WebP/MP4 per lesson (under 500 kB, `prefers-reduced-motion` shows the still, lazy loaded), generated in the site build so they never go stale. A narrated "first hour" video in the Coding Train tone for artists and makers is an owner decision (it is the one human-made asset worth making).
9. **"Ask the docs" without a service.** Value: medium, effort: medium; do after 1 and 2. Who: agent. Take: expose the docs over an MCP server (Mintlify generates one at `/mcp`) so a learner's own assistant can search them; a small static one reading the Pagefind index or `llms-full.txt` is enough. An in-page chat needs a paid model API and an abuse story: leave for the owner and note it in `backlog/later.md`. Low priority: a good search and idea 1 give most of the value.
10. **Classroom path (option H).** Value: medium for education, effort: low. Who: agent. Take: `zinc learn` (or `zinc dev docs/lessons`) that serves the lessons and the same Run buttons locally, offline, with the real native engine (the Go tour binary idea); can reuse the site build.
11. **A "Challenges" block at the end of concept pages (React).** Value: medium, effort: low once ideas 3 and 6 exist; only content work. Who: agent drafts, owner reviews tone.
12. **Versioned docs.** Value: low now, grows after releases; Starlight has no built-in versioning, so defer until the first API-breaking release.

Not recommended: WebContainers or Sandpack as the runtime (wrong runtime, company dependency); server-side compile (hosting, abuse); Monaco (size) unless a language server is wanted later.

## 5. Suggested order

1 and 2 first (days, no risk), then 3 (the first time a newcomer sees a program run in the docs), then the spike of 5 in parallel with 7. 6 follows 5. 8 to 12 as time allows.
