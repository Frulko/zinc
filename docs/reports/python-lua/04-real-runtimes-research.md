## 1. Python with no install

**python-build-standalone (PBS)**
- Owner is now astral-sh (repo `astral-sh/python-build-standalone`), licence MPL-2.0 for the project [V: `gh api repos/astral-sh/python-build-standalone`]. CPython itself is PSF [U].
- Cadence: latest release tag `20261026` (2026-10-26), 991 assets; contains CPython 3.11.18, 3.13.18, 3.14.10 [V: gh releases API]. Date-tagged releases, several per month in practice [U].
- Targets documented: aarch64/x86_64 apple-darwin, x86_64/i686/aarch64 windows-msvc, x86_64/aarch64 linux gnu and musl (+static), `armv7-unknown-linux-gnueabi` and `gnueabihf` ("Raspberry Pi 2 and later ... on many 32-bit Linux distros"), ppc64le, riscv64, s390x [V: docs/running.rst]. No armv6 (Pi Zero/1) asset in the listing grep and none in the doc [V]. No iOS/Android assets found in the release listing (grep for `ios|android` returned only musl lines) [V]: PBS does not cover mobile.
- Archive sizes, 3.14.10 `install_only_stripped.tar.gz`: macOS arm64 26.8 MB; Linux aarch64 gnu 30.6 MB; Linux armv7 gnueabihf 27.9 MB; Windows x86_64 23.3 MB; Linux x86_64 36.8 MB. The `pgo+lto-full.tar.zst` (with libs, headers, object files) is 63.8 MB (macOS arm64) to 115 MB (Linux x86_64) [V].
- Free-threaded builds exist for 3.13+ (`freethreaded-` flavours, also armv7) [V].
- libpython: PBS metadata has `libpython_link_mode` = static or shared and a `shared_lib`/`static_lib` entry in PYTHON.json ("may not be defined") [V: docs/distributions.rst]. So a libpython is shipped in the `full` archives; which flavour per target was NOT verified. Fully static musl builds "cannot load Python .so extensions" [V]: useless for numpy. Static libpython on macOS needs `libclang_rt` linking [V: quirks.rst].
- Quirks [V: docs/quirks.rst]: own libedit (terminfo lookup), no Tix, no `pip.exe` on Windows (use `python -m pip`), build-time paths baked into `_sysconfigdata`/Makefile/PYTHON.json (must be fixed up for relocation).
- Zinc fit: pinned URL + sha256 per target triple is natural (the release API gives names and sizes; digests are in `SHA256SUMS` [U]).

**uv**
- Apache-2.0 [V: gh API]; latest 0.13.7 (2026-11-03) [V]. Single binary tar.gz/zip: macOS arm64 14.3 MB, Linux aarch64 gnu 15.9 MB, armv7 gnueabihf 17.2 MB, Windows x86_64 15.2 MB, Linux x86_64 gnu 16.7 MB [V]. Also arm-musleabihf (armv6 hard-float) and riscv64 [V].
- uv downloads PBS builds itself ("managed" Pythons) [V: PBS running.rst]. `uv pip install --target DIR` exists: "packages installed at the top level of the directory", needs an interpreter only for resolution [V: uv CLI reference]. `--python-platform <triple>` installs for another platform ("advanced use cases") and `--only-binary` restricts to wheels [V: CLI reference, pip compat page]. The compat page itself does not mention `--target` [V: failure noted]. Not verified: whether `--python-platform` covers armv7, iOS or Android; the list printed started with windows/linux/macos/x86_64-pc-windows-msvc... (only the head was read).
- So the pinned toolchain could be: uv + PBS interpreter per host, then `uv pip install --target app/site-packages --python-platform <triple> --only-binary :all:` at build time (never on the user's machine for shipped apps).

## 2. Mobile and web

**iOS (PEP 730)**: Final, in 3.13, PEP 11 Tier 3 for `arm64-apple-ios` and simulator; no official end-user artefacts under Tier 3 [V: peps.python.org/pep-0730]. Wheel tags `ios_12_0_arm64_iphoneos`, `..._arm64_iphonesimulator`, `..._x86_64_iphonesimulator` [V]. Binary modules must be dynamic libraries each in its own Framework (not in site-packages), linked against `libpython3.x.dylib` (no static libpython) [V]. No subprocess, fork, spawn; no stdin; no pip at runtime [V]. BeeWare and Kivy shipped App Store apps, Pythonista and Pyto exist [V, in the PEP].
**Android (PEP 738)**: official embedding docs: only embedded mode with `libpython*.so` from a python.org Android build, stdlib as assets extracted at startup, JNI start; recommended tools Briefcase, Buildozer, Chaquopy, Flet [V: docs.python.org/3/using/android.html]. 3.14 notes "Binary releases for Android are now provided" [V]. Tag form `android_24_arm64_v8a` (PEP 738, API 24 floor) [S]. Android wheels built before Oct 2024 fail on 16 KB page devices [S: Chaquopy 17 notes].
**Which wheels exist**
- PyPI numpy 2.5.4: 66 files, none with `ios` or `android` in the name [V: pypi JSON]. It has musllinux aarch64/x86_64, cp315 and free-threaded wheels [V].
- PyPI pillow 13.0.0 has 9 iOS wheels (cp313/cp314, arm64 device, arm64 and x86_64 simulator, tag ios_13_0) and 0 android; cffi 2.1.1: 6 iOS; pydantic-core, cryptography, bcrypt, msgpack: 0 iOS, 0 Android [V: pypi JSON]. Android wheels on PyPI: 0 among the six packages checked [V].
- BeeWare's own index `pypi.anaconda.org/beeware/simple/numpy/` has numpy 2.3.5, 2.5.0, 2.5.2 (`.post1`) iOS wheels for cp313, cp314, cp315 (ios_13_0 and ios_17_0); 0 android entries on that page [V]. So numpy on iOS works but only from BeeWare's index, not PyPI.
- Chaquopy bundles numpy as a native package since 3.0.0 with OpenBLAS; its own repo builds Android wheels for all four ABIs [S: chaquo.com Chaquopy 17 notes]. Its wheels are Chaquopy-specific channel, not PyPI [S].
- cibuildwheel for iOS/Android: not verified (search returned nothing) [U].
**App Store**: Guideline 2.5.2: apps must be self-contained and may not "download, install, or execute code which introduces or changes features or functionality"; educational apps limited exception. 4.7 allows only HTML5/JavaScript mini apps, game emulators, plug-ins from non-embedded code [V: developer.apple.com/app-store/review]. The text never says "interpreter" [V]. Consequence: a Python interpreter plus the app's own bundled .py is accepted in practice (precedents in PEP 730) but pip at runtime on iOS is not allowed (PEP 730) and downloading Python code after review is a 2.5.2 risk.
**Pyodide** 314.0.7 (CPython 3.14) [V]. Download: `pyodide-core` tarball 6.76 MB bz2; full distribution 337.5 MB bz2 (page says "200+ MB") [V: gh release assets, docs]. Individual numpy wasm size and `pyodide.asm.wasm` size: not found [U]. Packages loaded via `pyodide.loadPackage`/`micropip.install` from `pyodide-lock.json`; wheels can be self-hosted [V]. Embedding next to another wasm module: no source found (Pyodide ships as its own Emscripten module + JS glue, loaded from CDN `cdn.jsdelivr.net/pyodide/v314.0.7/full/`) [V for CDN; the rest U]. Note: Pyodide's module is Emscripten with its own memory; sharing memory with a Zinc wasm module is impossible without JS marshalling [U].
**armv6/32-bit Pi**: piwheels (Raspberry Pi 3/4-built wheels) numpy 2.5.4 has `cp313 linux_armv6l` and `linux_armv7l` wheels (6 MB), 138 versions, 552 files; Bookworm Python 3.11 and Trixie 3.13 columns [V: piwheels.org/project/numpy]. Needs system libs (`libopenblas0-pthread`, libgfortran5) [V]. Tag is `linux_armv6l` (non-manylinux), so only piwheels serves it, and only for the distro's Python (3.11/3.13), not a PBS 3.14. PBS has no armv6 build [V]. PyPI numpy has no armv7 wheel [V, absent from the list]. So: armv6 = system Python from Raspberry Pi OS or skip.

## 3. Precedents and what went wrong

- Blender: bundles own Python; extensions bundle wheels under `./wheels/`, unmodified from PyPI, dependencies included, and listed in the manifest; for binary wheels you download one per platform with `pip download --only-binary=:all: --python-version=3.13 --platform=...` [V: docs.blender.org Python Wheels page]. This is exactly the "resolve for target, vendor wheels" model, and the best precedent for Zinc.
- godot-python (touilleMan): README says "Heavy refactoring in progress" for Godot 4, last push 2026-03-12, not archived [V]. py4godot (niklas2902): 329 stars, pushed 2026-11-01 [V]. Godot 4 status of either: not verified beyond that [U].
- Kivy / Flet: Flet's `serious_python` exists (README at `src/serious_python/README.md`); how it handles wheels not fetched [U]. Flet uses Pyodide for web [S].
- Unreal, Slicer, Krita, QGIS, Panda3D: no page fetched. Known from memory [U]: Unreal bundles its own Python (editor scripting); Slicer/QGIS/Krita embed Python with pip-style package install into a private dir; typical problems are version pinning vs. system Python and DLL clashes on Windows.
- Common pitfalls (sourced where marked): (a) C extensions need the matching ABI per OS/arch/Python version (wheel tags) [V]; the stable ABI helps: nanobind supports abi3 from Python 3.12 [V: nanobind docs] but numpy itself ships per-version cpXY wheels [V: PyPI list]. (b) GIL held by interpreter blocks the UI thread if Python calls are made on it: [U], general knowledge. (c) Mobile has no subprocess, no pip runtime [V].
- **CPython 3.14**: free-threading "officially supported" (PEP 779); single-thread penalty about 5-10% [V: whatsnew 3.14]. Multiple interpreters: `concurrent.interpreters` (PEP 734) exist; "many third-party extension modules on PyPI are not yet compatible with multiple interpreters"; object sharing limited to `memoryview`; each interpreter uses more memory than necessary [V]. So numpy in a subinterpreter is unreliable; a free-threaded build requires `cp314t` wheels (numpy has them on desktop/musl, [V]) but not on iOS/Android as far as the BeeWare list shows (only cp313-315 non-t) [V].

## 4. Bindings, GC cycles, event loop

- nanobind vs pybind11: nanobind claims 2.3x smaller instance (24 vs 56 bytes), smaller binaries, no LTO needed, vector calls; no numbers for call overhead on the page [V: nanobind.readthedocs.io/why.html]. Limited API/abi3: nanobind 3.12+ [V]. A direct Python C API (not limited) use is the simplest for a fixed embedded CPython (we pin the version): [U].
- Host object cycles: PyO3: types that own Python references implement `__traverse__` (visit each reference) and `__clear__` (break cycles); inside traverse no interpreter access [V: pyo3.rs]. That is the documented technique for a native object participating in Python's cyclic GC (tp_traverse/tp_clear). A host object that references a Python object but is NOT a GC-tracked Python type is invisible to the GC: cycle leaks [inferred from the PyO3 text].
- Pyodide: proxies of Python objects in JS are manual: "you must store the PyProxy and destroy() it when you are done"; returned proxies leak otherwise; `using` cleans at scope end; `toJs()` creates proxies that must be destroyed [V: pyodide type-conversions page]. The page does not mention FinalizationRegistry or cycles [V: failure noted]. Lesson for Zinc: define explicit lifetimes (handles scoped to a call or explicitly released).
- Not found: PythonMonkey and JPype GC docs (not fetched) [U]. PythonMonkey repo: Distributive-Network/PythonMonkey, 974 stars, pushed 2026-11-04 [V]; it embeds SpiderMonkey and CPython in one process.
- asyncio: no documented public single-step API. Documented approximation: `loop.call_soon(loop.stop); loop.run_forever()` runs one batch; `stop()` before `run_forever()` polls selector once with zero timeout and runs ready callbacks [V: docs.python.org asyncio-eventloop]. `call_soon_threadsafe` is the thread-safe entry [V]. `asyncio.run(loop_factory=...)` allows custom loops; policy system deprecated, removed in 3.16 [V]. `loop.add_reader/add_writer` for fds [V]. So tick-per-frame integration is possible with the stop trick; Zinc's libuv-based loop could pump asyncio's fds [U]. uvloop (libuv-based) latest v0.23.0 (2026-09-30) [V: gh]; its own loop is run via `run_forever`, no step API [U]. Pyodide WebLoop: not fetched [U].

## 5. Lua

- LuaRocks: MIT, v3.13.0 released 2026-01-28, repo `luarocks/luarocks` pushed 2026-10-29 [V: gh API]. 3.13.0 adds Lua 5.5 support [S: Wikipedia and openSUSE changelog via search]. Total rock count: not found (the stats page did not render) [V failure]. Standalone: a source tarball built with a C compiler plus an existing Lua [V: luarocks.org shows `wget luarocks-3.13.0.tar.gz`]; single-file standalone form: [U].
- Rock support for 5.5: luaposix's rockspec constrains `< 5.5` [S: lua-l thread Feb 2026]; lpeg is packaged for 5.5 on Alpine and Arch [S]. lua-cjson 2.1.0.17 rockspec: `lua >= 5.1`; luafilesystem scm: `lua >= 5.1`; luasocket scm: `lua >= 5.1` [V: raw rockspecs]. Whether they actually compile against 5.5 not tested [U]. Lua 5.4 coverage is broad (typical) [U]; compat between 5.1-5.4 C API is not binary compatible; rocks are rebuilt per Lua version.
- C rocks need a C compiler on the machine building them: LuaRocks reads `CC`; `zig cc` as CC: not verified [U], plausible. Pure-Lua rocks need no compiler.
- LuaJIT: MIT, last commit 2026-10-30 [V: gh]. 5.1 ABI, so 5.1-compatible rocks only; modern rocks mostly accept `>= 5.1` (above) but some need 5.3 integers [U]. Defold uses LuaJIT interpreter-only on iOS/consoles [S, from 01]. 
- Embedding symbols: C rocks expect `lua_*` symbols from the host process; on Linux the host must export them (`-rdynamic`/`-Wl,--export-dynamic` or a shared liblua loaded RTLD_GLOBAL); on macOS two-level namespace resolves with `-undefined dynamic_lookup`; Windows needs `lua55.dll` import: all [U], standard practice.
- Precedents (LÖVE, Defold, Neovim rocks.nvim, OpenResty, Solar2D): not fetched this session; all [U]. Known from memory: LÖVE and Neovim use LuaJIT; OpenResty uses LuaJIT; rocks there are installed by luarocks into a tree.
- Best compromise today: Lua 5.4 (broadest rock coverage, most rockspecs list `>= 5.1`/5.4 [U]); 5.5 supported by LuaRocks 3.13 but some rocks still pin `< 5.5` [S]. LuaJIT keeps 5.1 semantics and only where interpreter-only is acceptable. Choose 5.4 default, make the Lua version a pinned constant so 5.5 is a one-line change [inference].

## 6. Who tried it, risks

- Codon: `from python import` needs CPython installed; `CODON_PYTHON` must point to the libpython shared library (3.6+); operations use the CPython C API; imported library code runs at CPython speed [S: docs.exaloop.io, community write-up].
- Mojo: "doesn't include a CPython interpreter", uses the environment's default Python; `mojo build` doesn't bundle the packages, they must be present at runtime; import whole module only [V: mojolang.org docs]. Pinning via pixi/uv recommended [V]. This is the "install step" our rule forbids: both defer to the user's Python.
- PyO3 embed: auto-initialize and GIL attach exist ([V that traverse/`Python::attach` exist]; embed-specific docs not fetched [U]). nimpy: repo last pushed 2026-06-27 [V]; no analysis [U].
- No project found that ships its own pinned CPython + pip wheels inside a compiled non-Python host with no install, except Blender-style and BeeWare/Chaquopy-style app bundlers (all [V] above).

### Biggest risks
- Python: (1) numpy and other C wheels are missing on Android from PyPI, on iOS only via BeeWare's index [V], and absent for armv6/web-numpy sizes; (2) iOS needs Frameworks layout per extension and no runtime pip [V]; (3) size: 25-37 MB interpreter + 20+ MB for numpy [V for interpreter; numpy wheel on PyPI: 17-18 MB musllinux, V]; (4) the GIL on the UI thread, subinterpreters not supported by many extensions [V]; (5) cross-GC cycles.
- Lua: (1) rocks pinned per Lua version; 5.5 not universal [S/V]; (2) C rocks need a compiler and exported `lua_*` symbols; (3) LuaJIT's JIT unusable on iOS/consoles [S].

## Conclusions (max 10)
1. Ship per-target PBS archives (pinned `20261026`/3.14.10, sha256) for macOS, Windows, Linux aarch64/x86_64 and armv7 hf; 23-37 MB stripped each [V gh API].
2. Resolve wheels at build time with uv (`pip install --target`, `--python-platform`, `--only-binary`) and vendor them in the app, Blender-style; never pip on the user's machine [V uv CLI, V Blender docs].
3. Mobile Python is possible only for iOS/Android CPython Tier 3 builds with wheels per `ios_*`/`android_*` tag; numpy exists on iOS only on BeeWare's index and on Android in Chaquopy's channel, not on PyPI [V pypi JSON, V beeware index, S Chaquopy]. Mark mobile numpy as "from BeeWare/Chaquopy index" in any plan.
4. Web: Pyodide core is 6.8 MB, full 337 MB; packages come from `pyodide-lock.json`; it cannot share the Zinc wasm heap [V sizes, U heap].
5. armv6 Pi: only piwheels cp313 `linux_armv6l` numpy (6 MB) for the system Python; PBS has none, so unsupported by the pinned toolchain [V].
6. Handle lifetimes explicitly (scoped handles, `destroy()`-style release, or GC-tracked host types with traverse/clear) [V PyO3, V Pyodide].
7. Run Python on its own thread under the GIL with a per-frame message queue; drive asyncio with `call_soon(stop)`+`run_forever` or a thread and `call_soon_threadsafe`; do not rely on subinterpreters or free-threading yet [V docs 3.14, V asyncio docs].
8. Use Lua 5.4 as the default pinned version, 5.5 as the next flag; `lua >= 5.1` rockspecs of lfs/luasocket/cjson are fine, but luaposix pins `< 5.5` [V rockspecs, S lua-l].
9. Embedding rule is rarely free: Codon and Mojo both require an installed CPython at runtime, which Zinc forbids, so Zinc's design is not copyable and needs its own bundle layout [V Codon S docs, V Mojo docs].
10. App Store: bundled interpreter with app-shipped code is the safe zone; downloading Python or Lua code after review conflicts with 2.5.2 [V Apple guideline].
