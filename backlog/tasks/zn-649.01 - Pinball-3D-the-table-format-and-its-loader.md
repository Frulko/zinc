## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
One file describes a table, and nothing about a table is in code: playfield size and slope; walls and lanes as polylines with arcs; guides and one-way gates; flippers (position, length, angle range, strength); plunger lane; bumpers, slingshots, kickers and holes, drop and standup targets, rollovers, spinners, ramps with their rails, habitrails, drop holes and upper playfields as 3D paths with height profiles (edited as 2D paths plus heights); lights and their groups; for each element its physics (restitution, friction, kick force), its look (a primitive, or a mesh asset, material, colour, emissive) and its sounds per event; the rules as data (score per event, multipliers, missions with their steps and lights, ball save, extra ball); the camera and the panel layout for each orientation (landscape and portrait). A loader that validates and reports errors with the path of the offending value, versioned, with a written reference. (Owner request, 2026-10-10: a pinball all in real 3D instead of fake 3D, with a suited physics engine, a vertical table in the style of Space Cadet, parametrable in its lanes and assets, with a complete editor to make new tables, visual and sound.)

What exists (examples/pinball3d)
- src/format/schema.ts: a small schema engine (fields with type, default, limits, documentation): check() validates and fills defaults and reports every fault with its path, write() gives the canonical text, keysOf() lists an object's keys.
- src/format/table-schema.ts: the format, version 1, "zinc-pinball-table": 49 object kinds, about 300 fields.
- src/format/table.ts: the typed table (TableDef...), loadTable / parseTable / saveTable, the checks a schema cannot make (names that must exist, paths, profiles, what a rule's target must be), filesOf, groupsOf.
- src/format/source.ts: where a table comes from: FolderSource (zinc:fs), BuiltinSource (zinc:assets, assets/tables/<name>/), PackageSource (.zpinball: JSON with each file as text or base64), openTable, packTable.
- tools/table.ts: check, format, print, pack, doc.
- assets/tables/tidal-lock/table.json: the first table, "Tidal Lock" (355 lines): outer walls with a top arch, shooter lane with a one-way gate, two flippers, slingshots, inlanes and outlanes, three top lanes, three bumpers, a drop target bank, two standups, a spinner lane, a kicker that throws the ball in the air, a ramp that climbs 5.5 cm into a wire rail back to the left inlane, 20 lights, two decorative solids, 6 missions, 7 ranks, 24 rules, both layouts. Its coordinates are a first draft: ZN-649.02 tunes them with the game on screen.
- docs/pinball-table-format.md: printed by `tools/table.ts -- doc`, 49 sections, a field table and an example each.

Decisions
- The format is described once, as data (a schema), and everything follows from it: validation, defaults, the canonical text, the reference, and later the editor's forms. Scored against hand-written validators, writer and reference per element kind (fit 5/3, maintainability 5/2, effort 4/2): one definition cannot drift from its document.
- One list per kind of element (walls, bumpers, targets...) rather than one list with a "kind" field: every list has one shape, which the checker, the typed table and a palette per kind all want.
- Units: centimetres, cm/s, degrees; top view x right and y down the table, z up. The physics will use the same numbers (Jolt is tuned for moving things of 0.1 to 10 units: a ball of radius 1.35).
- Paths: [x, y] or [x, y, bulge] (the DXF convention: sagitta over half chord), a profile of [fraction, height] rows for ramps: compact, exact for arcs, and what an editor shows as handles and a curve.
- Canonical text: fields in schema order, a field at its default left out, rows of numbers and short objects on one line (150 columns), a named item per line. The fields that say what a line means (a rule's event, an action's "do", a condition's "test", a panel item's "show") are required so that no line reads `{ "value": 500 }`.
- Rules as rows a form can edit: when (on, event) if [test, target, is, value] do [do, target, value, mode, seconds]; missions as ordered steps (text, on, event, count, light); ranks, multiball, tilt, ball save and extra balls as their own small objects. "self" names the light of the element an event came from.
- A package is one JSON file with the files as text or base64: no archive code to write or vendor, and zinc:web has base64.
- Unknown fields are faults (with "did you mean"), so a typo is never silently dropped by a save.
- The name: "Tidal Lock" (it is data). A web search for a pinball of that name, and for "Heliopause", found none; not checked by hand against the Internet Pinball Database.

Worked around, proposed engine task
- "Object.keys, Object.entries and for-in over dynamic values" (size S to M: frontend builtin, runtime row, interpreter, AOT): a program cannot list the keys of a JSON.parse result today (Z0101 Cannot find name 'Object', Z0005 for...in), nor pass a replacer to JSON.stringify. keysOf() in schema.ts reads the keys from the engine's own JSON.stringify of the object (marked `ponytail:`); replace its body when the builtin exists. AC: `Object.keys(JSON.parse('{"a":1,"b":[2]}'))` is ['a', 'b'] on the interpreter, compiled and QuickJS.

Not in version 1 (the format is versioned so that they can come): a floor is flat and has no hole inside its outline (an upper playfield is a polygon at one height); a model collides as its box or its hull, not as its mesh; a gate is a line that passes one way, not a hinged flap. Tidal Lock has no sound, no music and no upper playfield yet (the format has them; ZN-649.03 adds the sounds).
