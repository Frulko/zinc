## Result (2026-11-09): GO, nothing to cut

`tools/build-wasm compiler` builds `build-wasm/zinc-compile.wasm` with the pinned zig 0.15.2 (no emscripten): the frontend, the checker, the IR, the optimiser, reference counting and the ZBC writer, through the driver `targets/wasm/compile_main.cpp`. It is a WASI command (`zinc-compile main.ts out.zbc`, engine files under `$ZINC_ROOT`, default `/zinc`). The build takes about 25 s from scratch (4 jobs, under 1 GB) and a second after.

What it took:
- **Exceptions.** The frontend and the IR parser throw and catch for control flow (a few dozen sites), and zig's libc++abi for WASI has no exception support. The build uses wasm exception handling (`-mcpu=generic+exception_handling -fwasm-exceptions`). It compiles libc++abi's `cxa_exception.cpp`, `cxa_personality.cpp` and libunwind's `Unwind-wasm.c` from the zig toolchain's own sources. Those objects come first in the link, ahead of zig's `cxa_noexception.o` stubs.
- **Files.** zig sets `_LIBCPP_HAS_FILESYSTEM=0` for WASI, which removes `std::filesystem` operations and `std::ifstream`. The build sets it to 1 and compiles libc++'s `filesystem/*.cpp`, `fstream.cpp` and `ios.instantiations.cpp` from the toolchain. wasi-libc covers the rest, including realpath.
- **Threads.** WASI's libc++ has no `std::mutex`. `targets/wasm/nothreads.h` (a forced include) supplies a lock that does nothing. `ir::parallelFor` runs serially under `__wasi__`, the one source change. `stubs.cpp` keeps its exception stubs only for builds without wasm EH.

### Decision
**Go.** The compiler is about 0.75 MB brotli plus 0.33 MB for lib/std, against the 3 to 8 MB gzip the benchmark expected. A 50-line program compiles in about 30 ms. Cut nothing: regex, filesystem, the exception runtime and fstream together are about 113 KB of 3.0 MB of code, while the compiler itself is 2.1 MB. Removing exceptions would mean rewriting the parser's and loader's error paths for maybe 5 to 10% of the code. RTTI is not used. Later and optional: `wasm-opt -Oz` (-17% raw, -6% gzip; binaryen is not pinned in the repo), and brotli on the server. Compile in a Worker on the playground page, since a UI lesson takes about 300 ms. A Worker needs no isolation.

### Can the web frame loop drop SharedArrayBuffer? Yes, with JSPI, at almost no cost
- The compiler needs no SAB at all.
- Today the run half (`targets/wasm/glue/worker.mjs`) blocks `host.gfxPoll` in `Atomics.wait` on a SAB, which needs COOP/COEP.
- **JSPI**: make `gfxPoll` a `WebAssembly.Suspending` import that awaits the page's next tick, with the input state in that message, and call `zn_run` through `WebAssembly.promising`. No C++ change and no size change.
  - Measured in Chrome 157 on a non-isolated page: 2.7 µs per suspend and resume through a MessageChannel, against 2.5 µs for the bare message. JSPI adds about 0.2 µs a frame.
  - Support: Chrome and Edge 137+. Firefox has an intent to ship and Safari's status is unverified (see links).
- **Fallback: Asyncify** (`wasm-opt --asyncify --pass-arg=asyncify-imports@zn.gfx`) on vm-web.wasm: 532,793 to 707,908 bytes raw (+33%) and 213,532 to 270,636 gzip (+27%). Its speed cost was not measured here; literature says it is modest when only one import is async.
- **Recommendation for ZN-774.30**: JSPI when `WebAssembly.Suspending` exists, the existing SAB path when the page is already `crossOriginIsolated`, otherwise the lesson's picture.
