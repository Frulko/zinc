## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
(Owner's answers, 2026-10-10, for the showcase demos of M27.) A museum updates the project (media, texts, sequences) without touching the table: the app checks a configured address for a newer signed project package, downloads it in the background, verifies it, and switches at the next idle reset; a bad or interrupted update leaves the current content in place. Built on what the engine has for app updates (zinc:system/update, the signed index), offline by default.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Done on the Mac (2026-10-11). Choice: the project package is the table itself as the engine's signed app update (zinc publish: the .zapp and stable.manifest signed with Ed25519), not a format of its own. Why: the signature, the SHA-256, the refusal of an older version, the staging and the rollback of a version that does not start are the engine's and already tested (ZN-324); a .zapp is rebuilt whole, so pictures baked in resources.bin change with the project; a content pack mounted over a running player would need Ed25519 in script and every cache of the player (images, 3D views, film copies) emptied in place. The address is the project's kiosk.updateUrl (the editor already writes it), the key is the table's zinc.json update.publicKey.
How: examples/museum-table/src/update.ts starts 'zinc update-app . --url <kiosk.updateUrl>' as a process (zinc:process) at the start and every hour, so a frame never waits for curl (the engine's update.check and update.download block, with no timeout); when it reports a staged version and the player is quiet (Player.quiet: no visit, none kept, no finger), update.restart(). Without kiosk.updateUrl nothing is started.
Engine: zinc update-app --url U (the channel when zinc.json has no update.url). Fix found by the test: update.restart() kept the ZINC_ASSETS and ZINC_PACKS that zinc run had set for the old version, so the new program played the old assets; the variables the engine set itself are now dropped before the restart (the user's own stay).
zinc.json of the table declares permissions fs, update, process (declaring any makes the others checked: museum_format failed on fs:read before fs was added).
Test: tests/t1/museum_update.sh, 12 s, server on a port the system gives (python3 -m http.server 0). Runs: no address (server log empty, ZINC_HAR entries empty, while 1.1.0 is published), channel edited after signing (refused), package cut to half (refused by SHA-256), update under a visit (downloaded during the visit, restart right after the reset, 1.1.0 plays sequence wave, finds itself up to date, current kept). The test's package is the sample without its photos and panoramas (29 MB instead of 98 MB).
Not proven: the frames of a headless run do not wait for the clock while the download does, so the test relies on the visit (8000 frames) outlasting the download (ready near frame 1200 on a loaded Mac); under heavy load it can fail with 'the story lacks a step'. No run in a window, no real remote server, no HTTPS address.
Limits (lines for later.md in the final report): a fused or exported table has no zinc command line, so it does not update; a published project that does not parse is taken (signature and hash only) and then shows an empty table that looks nowhere; the hourly period is a constant.
