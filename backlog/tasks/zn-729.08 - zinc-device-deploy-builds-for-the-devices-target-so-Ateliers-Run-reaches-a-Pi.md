## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Owner request (2026-10-12): deploy an app from Atelier on the Pi. deploy packs a .zapp for the workstation, which the device's engine must run itself: a Mac cannot put a drawing app on a Pi that way. ## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Done (2026-10-12, worktree agent). cmdDeploy (src/agent/client.cpp) asks info and maps os/arch/kind to a target of zinc export: the workstation's own system and architecture keeps the .zapp (arm64 = aarch64); linux aarch64 is rpi when kind holds 'Raspberry Pi', else linux; armv7l and armv8l rpi2; armv6l rpi1; x86_64 x86_64-linux; anything else (a Mac of the other architecture, riscv64) is refused by name. --target <t> and --pack decide instead (info is then not asked); both together are refused. One line on stderr before the build says which and why. The export is the one of zinc export, left in dist/<name>-<target>/; deploy reads its directory from export's last line and names the app after the project, as its .zapp does.

Decision (reversible, no number: for the coordinator): for the rpi targets, when ZINC_DISPLAY is not set and zinc.json names no board, display or targets.linux.display, deploy exports with ZINC_DISPLAY=fbdev and says so in its line. Why: an Atelier sketch has no zinc.json, a cross build without a driver runs on the null HAL and leaves after 60 frames, and the prototype's Pi targets draw on the framebuffer; the driver gives the screen back when /dev/fb0 is missing. Only in deploy: zinc export itself is unchanged.

Test switch: ZINC_AGENT_AS='os arch kind', read by the agent's info (server.cpp, infoJson).
