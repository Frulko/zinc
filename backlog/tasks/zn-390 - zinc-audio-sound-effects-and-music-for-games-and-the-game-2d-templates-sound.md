## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by ZN-317.01: next/ has no audio API (no zinc:audio, no WebAudio in zinc:web), so the game-2d template has no sound. Pick a proven library (miniaudio, MIT-0 / public domain, single header) behind a zinc:audio module: load a WAV / OGG asset, play / stop / volume / loop, a short beep generator; a null backend headless; then add a jump / coin sound to templates/game-2d.

**Decisions** (to file; each is reversible).
1. miniaudio lives in `plugins/audio/vendor/`, not `third_party/miniaudio/`: plugin.json sources are relative to the plugin, the build key hashes the plugin's files, and a plugin is split into its own repository and installed by `zinc add`, so it must carry what it compiles (sqlite's amalgamation is the precedent). The README row and PIN keep RULES section 3.
2. A Zinc stand-in `native/audio.sim.ts`, and neither `"deterministic"` nor `"live"` in the manifest: the native code wins in a normal run whenever it builds, a deterministic run binds the stand-in and builds nothing. Without it tests/t0/zapp.sh and fuse.sh (game-2d, fresh ZINC_HOME) would compile miniaudio or download the toolchain, and a machine that cannot build the plugin could not start the template. Written in the subset both engines read, it is also the prototype's sim. Cost: two silent backends; silent.ts keeps them answering alike. The stand-in decodes nothing (duration 0 for files, mix() silence).
3. The engine owns no device and always mixes 48 kHz stereo; a `ma_device` opened on a pthread pulls it. Scores (fit x3, perf x3, size x2, maintainability x2, risk x2, portability, effort): device opened at the first play 3,1,5,5,4,5,5 = 50 (a frozen frame of 90 to 520 ms in the game); opened at load() on the program's thread 4,2,5,5,4,5,5 = 56 (that much added to every start); opener thread 5,5,5,4,4,4,4 = 64, chosen. One mixer path for both backends; a device at another rate gets the mix converted by miniaudio. Revisit if the double conversion of 44.1 kHz material is heard, or for Windows (pthread).
4. Sounds are kept as float samples, not 16-bit: miniaudio 0.11.25 (and its master on 2026-10-10) loses the end of any non-float sound. In `ma_engine_node_process_pcm_frames__sound` the slow path fills the sound's 512-frame cache, gets MA_AT_END on the read after the last partial one, sets atEnd and leaves the loop with the converted frames still in the cache; the next call sees atEnd and stops. Measured with 16-bit WAV: 960 frames -> 512 heard, 2000 -> 1536, 480 and 240 -> none. Float sources take the fast path and are whole (clips of 240 and 480 frames are heard to their last frame, a 4800-frame tone gives its 200 crossings). Cost: twice the memory, 21 MiB per minute of 44.1 kHz stereo. Worth reporting upstream (the owner's step: outward-facing); revisit when fixed.
5. `tone(..., 'noise')` uses our xorshift32, not `ma_noise`: its white noise is all positive in 0.11.25 (2400 frames, 0 zero crossings, values 0 to amplitude), a constant offset.
6. `load()` never throws: a missing or undecodable file is a silent Sound (`ok`, `error`) and one `console.warn`. A sound must not stop a game (Raylib's LoadSound, zinc:video's `add` returning false, zinc:webview's warning for a missing asset).
7. Each `play()` is a new voice (a coin rings over the previous one, as Howler does); 32 voices, the oldest one-shot gives way and a loop only when every voice loops. No pause, seek, pitch, pan or fades: not asked, and ZN-573 builds the Web Audio facade on this.
8. Time stands still on the null backend and only `mix()` moves it: a headless run is repeatable and a test can read what a game plays. A program that waits for `playing` to fall will wait; `ZINC_AUDIO=null` gives the same silence in a windowed run.
9. tests/t0/fuse.sh packs the game with ZINC_DETERMINISTIC=1 (tests/run exports it already; said in the script so it also holds when run by hand).
