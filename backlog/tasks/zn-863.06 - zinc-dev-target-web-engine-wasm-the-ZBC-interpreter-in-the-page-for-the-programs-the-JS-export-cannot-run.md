## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Done 2026-11-09 (worktree agent).
- zinc dev <dir> --target web --engine wasm (--engine js is the default; wasm refuses --lan, --render, --prepare): devWasm in src/cli_web.cpp runs 'zinc export --target wasm -o build/.zinc-web-dev/wasm' (the ZBC, vm-web.wasm built incrementally by tools/build-wasm, the glue of targets/wasm/glue), adds a reload script to its index.html, and serves the folder on 127.0.0.1 with COOP/COEP (the glue's frame loop waits on a SharedArrayBuffer), the Host check of the dev server (DNS rebinding) and no dotfiles. A save builds again (~0.4 s) and the page reloads through a long poll (/__zinc/wait?v=N): a new worker and canvas each time (an OffscreenCanvas is transferred once, a wasm instance does not start over). A failed build shows its errors under the canvas until the next good one. Lifecycle: WasmDev::Build {Building, Ready, Failed} + version, changed by built() only, under its mutex.
- examples/hero says exactly what it lacks: the engine (src/rt/machine.cpp Machine::load) now names every missing native module at once: 'the native modules 'SvgEngine', 'Lottie', 'Video' are not linked into this engine' (was the first one only; one module keeps the old text, native_call T0 passes). examples/breakout runs (90 frames, last frame captured: the title screen), a save reloads it.
- docs/targets/web.md 'Two engines: JavaScript or the interpreter in WebAssembly' (table: what runs, behaves like, draws, plugins, hot reload, speed, needs; when to pick wasm); docs/targets/wasm.md 'Under zinc dev'.
Decision (for the coordinator to record): zinc dev --engine wasm reuses zinc export --target wasm and the SharedArrayBuffer glue (app.js) served with COOP/COEP, not the JSPI worker of the playground: the dev server controls its headers, so isolation is free and works in every browser with SharedArrayBuffer, where JSPI is Chrome/Edge 137+ only (Firefox unclear, Safari none). Full page reload on save, not module swap: a bytecode module has no per-module swap and a fresh worker is the only clean restart of a wasm instance (and of a JSPI-suspended loop). Default stays --engine js (Flutter's and Kotlin's pattern: JS by default, wasm by flag).
Research (sonnet sub-agent): Flutter renderers and --wasm https://docs.flutter.dev/platform-integration/web/renderers.html , https://docs.flutter.dev/to/wasm ; JSPI shipped in Chrome 137 https://web-platform-dx.github.io/web-features-explorer/features/wasm-jspi , https://v8.dev/blog/jspi-newapi , Firefox status https://caniuse.com/mdn-webassembly_jspi ; transferControlToOffscreen once per canvas https://developer.mozilla.org/docs/Web/API/HTMLCanvasElement/transferControlToOffscreen .
Numbers: first start 0.5-3 s (hero 2.9 s with the ZBC of 1.8 MB, breakout 0.5 s); a save rebuilds in ~0.4 s; vm-web.wasm 0.6 MB; tools/build-wasm from scratch in a fresh tree 13 s.
Proof: tools/web-dev-wasm-test build/zinc tests/fixtures/web-dev-wasm: rebinding, runs, error, reload pass. Headless Chrome: hero prints the three missing modules; breakout frame 90 captured.
Proposed tests: tests/t1/web_dev_wasm.sh (written, ~15 s, Chrome ~300 MB); tests/t0/native_call.sh (the module message, 5 s).
