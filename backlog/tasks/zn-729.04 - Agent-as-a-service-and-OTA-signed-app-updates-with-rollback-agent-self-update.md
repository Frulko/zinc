## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`zinc agent install|uninstall` writes the systemd unit or the launchd agent so the daemon starts with the machine. OTA: an app whose zinc.json has update.publicKey is only replaced by a .zapp signed with that key and of a higher version, pushed (`zinc device <d> install`) or fetched from its channel (`zinc device <d> update <app>`, zinc update-app on the device); the previous version is kept and comes back when the new one does not start. The agent updates the engine with zinc update.
<!-- SECTION:DESCRIPTION:END -->

Decisions (no number taken; for the coordinator):
- Pushed updates are checked with the detached signature of zinc sign (<file>.sig, sent as 'sig' in the install request, zn::tc::verifyBytes); channel updates with the signed manifest of zinc publish and its SHA-256 (zn::tc::fetchManifest, downloadUpdate). The key that decides is the installed app's. The first install and uninstall-then-install need no signature: a paired workstation already has the user's rights, the signature guards against a wrong or stale build. No cryptography written.
- Rollback happens at run: an update on trial (apps/<name>/trial, previous.zapp a hard link) that ends with an error within 5 s (ZINC_AGENT_TRIAL_MS) is replaced by the previous version, which is started; the client gets the refusal with the end of the update's log and exits 1. Still running or status 0: it holds, the previous version is removed. Stopped (SIGTERM, SIGKILL): still on trial. Only signed apps keep a previous version, so the dev loop of unsigned apps is unchanged.
- zinc device update leaves a running app running (the agent does not know its arguments); the new version is the one the next run starts.
- The service is per user, never root: launchd agent at login (the apps can open windows), systemd user unit with lingering at boot, KillMode=process so apps outlive the agent.
- The engine: zinc device update does what zinc update does (verified download into ~/.zinc/updates) and stops there.
